## 2. 密钥派生链（唯一权威定义）

两条链共用 `seed + 证书 DER + 包名`，但 master 组成不同——
**这是刻意的，改动前必读 §5.1**。

### 2.1 段密钥（壳 so 的 `.bitcode`）

```
master = SHA256( seed_8(LE) || CRC32(.text)_4(LE) || "dpt-kl-v1" )
salt   = SHA256( certDER )
info   = "dpt-sec-v1" + pkg
key    = HKDF-SHA256(ikm=master, salt=salt, info=info, len=16)   // RC4
```

- `seed`：root `build.gradle` 生成、持久化在 `build/dpt-build-ids.properties`，
  经 `-DDPT_KL_SEED` 传给 4 个 ABI，并落盘 `shell-files/keyladder-seed.txt`
- `CRC32(.text)`：**小端 4 字节**（Java 侧必须显式 `ByteOrder.LITTLE_ENDIAN`）
- `certDER`：打包侧取 `--cert-source`（默认 `-f` 输入）的签名证书；
  运行期从**已安装 APK** 提
- 每个 ABI 的 so 各自加密自己的 `.bitcode`（故可以绑定 `.text`）

### 2.2 配置 + dex 载荷

```
master_cfg = SHA256( seed_8(LE) || "dpt-cfg-master" )      // 刻意不含 CRC
salt       = SHA256( certDER )
info       = "dpt-cfg-v1" + pkg
material   = HKDF-SHA256(master_cfg, salt, info, 48)
             = [ aes_key(32) || iv(16) ]
```

- `aes_key` 同时用于：配置 `xixin_config` 的 AES-CBC 解密、
  dex 载荷 `xixin_data` 的 ChaCha20 区块解密
- **不含 CRC 的原因**：配置只有一份，而 4 个 ABI 的 `.text` CRC 各不相同
  （arm=`0xf38fa79d` / arm64=`0xbbb30a8d` / x86=`0x359a023e` /
  x86_64=`0xe50120a1`），掺进去会导致同一配置跨 ABI 解不开

### 2.3 产物里没有任何密钥材料

`DPT_UNKNOWN_DATA` 符号已删除。运行期所需的全部材料都是现算的。
运行期 APK 路径由 Java 在 `System.load` 之前
`Os.setenv("DPT_APK_PATH", sourceDir)` 传入（`init_array` 里 `/proc/self/maps`
还没有 `base.apk`，见 §5.2）。

## 5. 已修复的失效链（防止回退）

### 5.1 v1.2.3 ~ v1.3.2 的完整失效史

| 版本 | 现象 | 根因 |
|---|---|---|
| v1.2.3~v1.2.5 | 启动 SIGABRT | `computeMaster` 的 CRC32 用 `ByteBuffer.putInt`（大端），C 侧 ARM 小端 → key 不一致 |
| v1.2.6 | 仍 SIGABRT | `init_array` 时 `/proc/self/maps` 尚无 `base.apk`；so 在 `dpt-libs/` 无 `/lib/` 可反推 |
| v1.2.7 | 仍 SIGABRT | `apk-path` 文件方案；`Log` 被 `-assumenosideeffects` 编译成 no-op，写失败静默 |
| v1.2.8 | `java_class == null` | v1.2.3 误删 `DPT_UNKNOWN_DATA` 写入 → 配置解密失败 |
| v1.2.9 | **能启动**（旧基线） | 恢复符号写入 |
| v1.3.0 | — | P0/P1/P2；但 P2「相邻字面量拆段」被编译器合并，**实测无效** |
| v1.3.1 | `materializeBlock() inflate failed` | P0 只改配置链，漏了 dex 载荷链（两者原本都用 `encKey`） |
| **v1.3.2** | **全通过** | 载荷密钥也改用派生材料 |

### 5.2 四条必须记住的教训

1. **删一个"共享载体"前必须列全消费者**
   `encKey` 同时喂配置链与载荷链。删 `DPT_UNKNOWN_DATA` 时只看到一条，
   造成 v1.2.8 和 v1.3.1 两次断链。做法：`grep -rn` 符号名 + 搜索全部使用点。

2. **对拍参数不能取退化值**
   `TEST_CRC = 0` 时大端小端字节相同，字节序 bug 被完全掩盖。
   现在用非零 CRC + 真实证书硬编码期望值。

3. **声称"已验证"前必须真跑**
   v1.3.0 的 P2 我只看源码就写"产物里不成词"，实际相邻字面量在编译期
   被合并。验证要落到真实产物（`strings`、`readelf`、实际解压）。

4. **fail-closed 必须带分步日志**
   没有 `[kl] apk=... derive_rc=` 这类现场，`SIGABRT` 只能靠猜。
   本项目因此多花了 3 轮。

## 6. 已知残留（不在本基线修复范围）

| 项 | 说明 |
|---|---|
| `JNI_OnLoad` / `JNI_OnUnload` 导出 | JNI 必需，无法隐藏 |
| `Java_*` 业务符号导出 | dex2c 走短名绑定，隐藏即 `UnsatisfiedLinkError` |
| libc 导入符号 | 暴露所用能力（`__android_log_print`、`dladdr` 等） |
| P2 的边界 | 只挡静态 `strings`；动态调试下断点读 `dpt_kl_info_prefix()` 仍能拿到明文 |
| 配置链不含 CRC 自绑定 | 见 §2.2，是跨 ABI 的必要取舍 |
