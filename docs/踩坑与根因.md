## 一、现象

- **v1.0.0**：正常，能启动。
- **v1.0.1 / v1.0.2 / v1.0.3**：打包出的 APK 一点都跑不起来，启动即闪退。
- **v1.0.4**：恢复正常。

真机崩溃栈（Redmi / Android 16 / `com.xixin.box`）：

```
#00 pc 0x58078   /data/data/com.xixin.box/dpt-libs/arm64/lib*.so
#01 pc 0x44a24   lib*.so
#02 pc 0xa42dc   lib*.so
#03 pc 0xa45c4   lib*.so
#04 pc 0x2250cc  /apex/com.android.art/lib64/libart.so
      (art::ClassLinker::DefineClass(...)+4940)
#05 pc 0x23641c  libart.so (FindClassInBaseDexClassLoader)
#06 pc 0x6140ec  libart.so (VMClassLoader_findLoadedClass)
```

崩溃点全部落在 `libdpt.so` 内部，调用方是 ART 的 `ClassLinker::DefineClass`
—— 即**壳在 ART 定义类的路径上还原指令时出的问题**。

## 二、引入点

```
9f9d2dd  feat: OoooooOooo v4 载荷格式 + 打包侧 IO 优化 + 基准工具
```

v4 把密文与方法的配对方式从 **「按 `methodIdx` 索引寻址」** 改成
**「按类内位置递增配对」**（runtime 遍历一个类的每个方法，就按顺序消费一条
`MethodData` 记录）。方向没错，但这次重构**静默推翻了三个旧前提**，
形成三个各自独立、都能致命的缺陷。

## 三、三个根因

### 根因一：解密指令写入只读 dex 页（1.0.1~1.0.3 闪退的首要原因，1.0.4 修）

**提交**：`0af9fbf` 引入，`c4f41df` 修复。

`0af9fbf` 判定 `change_dex_protective()` 与 `dexMemMap` 是「v4 改造后失去调用者的
死代码」并删除。但它没注意到：写 dex 的职责虽然从 `patchMethod` 搬到了
`patchMethodInsns`，**写权限保障却没跟着搬**。

v1.0.0 的 `patchMethod` 在写之前必调 `change_dex_protective()`，把
`[begin, begin+dexSize)` 设为 `PROT_READ|PROT_WRITE`，并用 `dexMemMap` 做 memo。
删掉之后，只剩 `hook_mmap` 里的 `fake_mmap` 一个兜底 —— 而 `fake_mmap` 只对
**经过被 hook 的 libc `mmap`** 加载的 dex 生效。

**代码里的直接痕迹**：`patchClass` 取到了 `dexSize` 却从不使用 —— 它正是
`change_dex_protective` 需要的第二个参数。一个「取了不用」的参数，指向一次
「删错了东西」。

复核确认 1.0.1（`f2580f8`）的写权限防线**完全押在 `fake_mmap` 这一个单点上**：

| 检查项 | v1.0.0 | v1.0.1 (f2580f8) |
|---|---|---|
| 显式 `mprotect` 调用 | 有 | **全文零次** |
| `dexMemMap` memo | 有 | **不存在** |
| `change_dex_protective` | 有 | **不存在** |
| 调用点 | 有 | **无** |
| `fake_mmap` 升级 `PROT_WRITE` | 完好 | 完好 |
| `hook_mmap()` 已安装 | 是 | 是 |

**修复**（`c4f41df`）：恢复 `change_dex_protective()`，参数改为 `uint64_t dexSize`
（`patchClass` 里 `dexSize` 已是 `uint64_t`，传 `int` 会截断大 dex），
在 `class_data_off_ != 0` 分支内、`findClassIndex` 之前调用，并恢复 `dexMemMap` memo
与 `<map>` 头文件。

> ⚠ **现状（v1.0.9）**：以上是 **v1.0.4 的历史修复方案，已被取代**。
> `change_dex_protective` 与 `dexMemMap` 现在在 `shell/src/main/cpp/` 中**引用数均为 0**。
> v1.0.7 的 Task 1.5 把「整 dex 无条件 RW」换成了**页粒度开窗 + 写完关窗**
> （见 §十）。**不要**照本节去「恢复」这两个符号。本节保留是为解释 v1.0.1~v1.0.4
> 的崩溃链。

**关键约束**：只调用一次 `mprotect`/dex，**不能**放进 `patchMethodInsns` 的每方法路径
—— `patchClass` 运行在 ART 的 class-loader 锁内。

> ⚠ **现状（v1.0.9）**：约束本身仍成立（每 class 只有一个开窗阶段、一个关窗阶段），
> 但粒度已从「整 dex 一次 `mprotect`」改为「按页合并成 run，每个 run 一次 syscall，
> 见 `dpt_hook.cpp:757`」。

### 根因二：`getMethodData` 边界检查基准错误（1.0.2 修）

**提交**：`9f9d2dd` 引入，`69a8741` 修复。

```cpp
// 修复前
const uint8_t* base = m_buffer + m_methodDataOffset;
size_t off = entry->methodDataOff;
for (uint16_t i = 0; i < index; i++) {
    if (off + 6 > m_size) return view;   // ← 基准错了
    uint16_t sz = readUInt16At(base, off + 4);
    off += 6u + sz;
    if (off > m_size) return view;       // ← 基准错了
}
```

`methodDataOff` 是**相对 methodData 区起点**的偏移，却拿去和 **payload 总长 `m_size`**
比较。methodData 区远小于 payload 总长，所以合法范围内的 `off` 永远小于 `m_size`，
这个检查形同虚设 —— 越界值只要没超过总长就会被放行，`readUInt16At` 直接读到缓冲区之外。
payload 是 `mmap` 出来的，越界读就是 SIGSEGV。

**为什么测试没抓到**：跨语言对拍用的 payload 只有 126 字节，构造的越界值恰好没超过
总长，两种算法都「通过」了。这是**测试覆盖不足，不是算法侥幸正确**。
本次用 ASan 复现 —— 旧算法直接报 heap-buffer-overflow。

**修复**：统一基准，用 methodData 区剩余长度 `avail = m_size - m_methodDataOffset`
做全部四处比较。

### 根因三：载荷方法错配（1.0.3 修）

**提交**：`9f9d2dd` 引入，`5ed1332` 修复。

v4 契约要求：打包侧对 runtime 遍历到的**每个**方法都产出一条 `MethodData` 记录。
但 `DexUtils` 有四处 skip 是**不产记录**的：

- `method.getCodeOffset() == 0` —— abstract / native
- `code.getInstructions().length == 0` —— 空方法体
- `insnsCapacity * 2 < return 长度` —— 容量不足
- `getCodeOffAppearCount() > 1` —— code_item 被多方法共享

其中**任何一处 skip 都不只是少保护一个方法**，而是把它之后的所有方法**整体错位一格**：
前一个方法的密文被写进后一个方法的方法体。ART 在 `ClassLinker::DefineClass` 里
一边解密一边校验 dex，于是直接 `VerifyError` / SIGSEGV。

**为什么 v1.0.0 不中招**：它建 65536 槽的表并用 `codeItemVec->at(methodIdx)`
**按索引**取密文，缺一条记录只影响那一个 `methodIdx` 本身，不会波及后续方法。

**修复**：新增 `placeholderInstruction()`，让上述四处 skip 改为产出一条
`insnsSize = 0` 的占位记录（6 字节，带正确的 `methodIdx`）。runtime 的
`patchMethodInsns` 见到 `insnsSize == 0` 立即返回，什么都不写，方法体不被触碰；
位置配对因此恢复恒等。

class 级的三处 `continue` 不需要改：类被排除时它的方法体根本没被抽空，
native 侧 `findClassIndex` 返回 `nullptr` 会整体跳过该类，不存在错位。

**实测数据**（真实 APK）：

| APK | dex 数 | 记录数 == 遍历数 | 错配 |
|---|---|---|---|
| orig.apk | 21 | 222837 == 222837 | 0 |
| target.apk | 1 | 9448 == 9448 | 0 |
| min2.apk | 1 | 32 == 32 | 0 |

修复前 `target.apk` 上有 **126 个方法坏掉**（31 无记录 + 95 密文错配）。

## 四、为什么必须三个都修

前两个根因各自足以致命，**修完前两个仍会崩**，因为第三个还在。修复过程本身就是
一次消减实验：

| 版本 | 修了什么 | 实测结果 |
|---|---|---|
| v1.0.2 | 根因二（边界基准） | **仍崩** |
| v1.0.3 | 根因三（载荷错配） | **仍崩** |
| v1.0.4 | 根因一（只读页写入） | **恢复** |

这条链把因果关系钉死了：既然修完前两个还崩，就**必然**存在第三个独立缺陷；
而唯一剩下的、且修完就不再崩的，就是根因一。

## 八、教训

1. **删除「死代码」前，先确认它是否承载了某个副作用。** `change_dex_protective`
   的调用者没了，但它的**职责**（保证 dex 页可写）仍被别的路径需要。
   一个「取了不用」的参数就是这类遗漏的痕迹。
2. **改配对契约时，要同步清点所有不产记录的路径。** 从「按索引寻址」改成
   「按位置配对」，等于把所有 skip 从「局部影响」升级成「全局错位」。
3. **对拍测试的输入太小会掩盖基准错误。** 126 字节的 payload 让错误基准
   「恰好通过」；关键边界要用 ASan 或真实规模的数据压。

## 九、v1.0.5 触发 / v1.0.6 修复：内存加载路径的地址白名单拒绝（VerifyError）

> 2026-10 新增。Task 1.4（InMemoryDexClassLoader 内存加载）在 **v1.0.5**
> 真机首跑即触发，由 `--disable-inmemory-dex` 对照实验定案；
> **修复在 v1.0.6**（`dc3eaee`）。

### 现象与对照实验

同一工具、同一 App（`com.xixin.box`，14 dex，Redmi / Android 16）：

| 打包方式 | 结果 |
|---|---|
| 默认（内存加载） | **必崩** `java.lang.VerifyError: Verifier rejected class com.xixin.box.xiApplication` |
| 加 `--disable-inmemory-dex` | **正常启动** |

崩溃特征：`xiApplication` 的 8 个方法全部是垃圾字节；dex 位置
`/data/user/0/com.xixin.box/Anonymous-DexFile@2086524492.jar!classes14.dex`
（`!classes14.dex` 后缀证明内存路径已生效，dexIdx=13）。

对照实验一次定案：payload、配对、契约、打包侧提取全部正常（文件模式能跑），
**唯一变量是内存加载路径下 patch 从未发生** —— 方法体保持打包时的随机填料
（默认 `obfuscate = !smaller = true`），verifier 拒绝。

### 根因（演绎闭合）

`patchClass` 的 gate（`is_shell_dex_location`）是内存/文件模式唯一的差异环节：

```cpp
location 含 "i11111i111.zip"                          → 文件模式，放行
location 含 "Anonymous-DexFile" && isShellInMemoryDex(begin) → 内存模式
```

崩溃 location 含 `Anonymous-DexFile` → 前缀条件命中 →
**必然结论：`isShellInMemoryDex(begin)` 返回 false**，即 ART 交给
`DefineClass` 的 `DexFile::begin_` 不落在 shell 注册的
`[NewDirectByteBuffer 地址, +size)` 区间内。Android 16 的 ART 没有把我们
注册的 buffer 地址直接暴露给 DexFile（注册端注释原断言「ART 引用不拷贝
（NonOwningMemoryRegion）」——该断言此前无源码依据，本次实验证伪其推论）。

gate 失败后**无任何日志直接 return**（release 构建下所有 `DLOG*`/`NLOG`
又被编译掉，`dpt_log.h` + `CMakeLists.txt` 仅 Debug 定义 `DEBUG`），
于是零日志、8/8 方法全坏、VerifyError —— 三个症状与该机制完全吻合。

被排除的备择假设：跨语言 payload 契约不一致（逐字段核对一致）、
`ClassIndexEntry` 布局不一致、`parse_dex_number`（对 `classes14.dex` 正确
返回 13）、methodIdx 错位（会打 `payload order mismatch` 日志且 8/8 全坏
不可能）、打包侧 HashMap 竞态 / 空 catch 截断（代码 1.0.4→1.0.5 未变更，
且文件模式能跑证明 payload 完整）。

### 修复

1. **`dpt.cpp` 注册表加内容指纹**：`registerShellInMemoryDex` 登记时快照
   112 字节 dex header；`isShellInMemoryDex` 先按地址（快路径），未命中再
   `memcmp` header 内容。dex header 含整文件 checksum + SHA-1 signature，
   外来匿名 dex 不可能碰撞，原保护语义（防误 patch 应用自己的
   InMemoryDexClassLoader）保持不变。
2. **`dpt_hook.cpp` gate 拒绝时补错误日志**，消除这类静默失败的排障盲区。
3. 修正注册端「ART 引用不拷贝」的过强断言注释（`dpt.cpp` / `dpt.h`）。
4. **新增 `ELOG` 常开错误日志机制**（`common/dpt_log.h`）：release 构建原本把
   所有 `DLOG*`/`NLOG` 编译成空，这是本次"崩溃日志只有一句 VerifyError"的
   直接原因。`ELOG` 在 Debug 与 Release **都**编译，仅用于失败分支
   （gate 拒绝、payload/解密失败、hook 装载失败、内存路径回退、zip/落盘
   失败等），覆盖 `dpt_hook.cpp` / `dpt.cpp` / `dpt_util.cpp` /
   `dex/MultiDexCode.cpp` / `dpt_crypto.cpp` 全部失败分支，正常启动零输出。
   Debug 构建的日志行为完全不变；防御逻辑零改动。
   **`dpt_risk.cpp` 故意不换**：其日志全是 DLOGW/DLOGD（防御触发与
   "检查被跳过"），常开等于向攻击者透露检测机制是否生效 → 削弱防御。
   覆盖审计：CMakeLists 全部 24 个源文件 + 全部自有头文件已逐一读过，
   无剩余 DLOGE（其余文件零日志）。

patch 目标本就是 ART 的 `begin_`（无论它是我们的 buffer 还是 ART 自己的
拷贝），所以指纹放行后写入即生效，无需关心 ART 内部如何处理 buffer。

## 十、v1.0.8：`restoreRead` 用途混用，RW 窗口被误跳过（v1.0.9 修复）

### 现象

v1.0.8 打包 `com.xixin.box` 冷启动崩（`docs/crash.log`，2026-10-07，
Redmi dash / Android 16 / arm64）。这是**崩溃诊断能力（本文第二部分）
上线后第一次真机崩溃**，日志第一次带上了状态，直接定案：

```
F/libc : Fatal signal 11 (SIGSEGV), code 2 (SEGV_ACCERR), fault addr 0x7b4f924d10
F/DEBUG: Abort message: 'SIG11 addr=0x7b4f924d10 code=2
  loc=/data/user/0/com.xixin.box/Anonymous-DexFile@3818887144.jar!classes14.dex
  restoreRead=0 mprotect=-1 methodIdx=1038'
```

- `code 2` = `SEGV_ACCERR`：地址有映射但**权限不对**（不是未映射）
- `restoreRead=0` + `mprotect=-1`：代码判定「不必开窗」，且**从未尝试开窗**
- 崩在 `patchMethodInsns` 往 dex 写回明文那一刻（`#00` 在 dpt 自己的 so，
  `#04` 是 `art::ClassLinker::DefineClass`），冷启动加载 Application 时

### 根因

`dpt_hook.cpp` 里 `restoreRead` **一个变量管了两件事**（行号属 **v1.0.8**；
修复后位置会因注释增删而漂移，以下按符号描述）：

```cpp
const bool restoreRead = is_file_dex_location(location);

if (restoreRead && UNLIKELY(dpt_mprotect(... RW ...) != 0)) { ... }  // ← 用途A：是否开窗
...
if (restoreRead) { ... dpt_mprotect(..., PROT_READ); }              // ← 用途B：是否关窗
```

`is_file_dex_location()` 只认 `i11111i111.zip`：

```cpp
return location.rfind(DEXES_ZIP_NAME) != std::string::npos;
```

而 ART 以**文件方式** mmap 的 shell dex，`location_` 同样带 `Anonymous-DexFile`
（见日志 `loc=`）→ 被误判为内存 dex → `restoreRead=false` → 用途 A 短路 →
**窗口从未打开** → 写只读页 → `SEGV_ACCERR`。

**引入点**：v1.0.7 的 Task 1.5 重写。`git diff v1.0.6 v1.0.7` 显示
`change_dex_protective()` 的**无条件** `mprotect(RW)` 被换成了被 `restoreRead`
门控的版本。v1.0.8 对该文件是**纯新增 234 行诊断、0 行删除/修改**
（`git diff v1.0.7 v1.0.8` 在 `dpt_hook.cpp` 的 `^-` 行数 = 0），
所以它没引入也没加重 bug，只是让同一处崩溃**带上诊断**而暴露出来。

### 为什么 Task 1.5 要引入 `restoreRead`

方向是对的。v1.0.6 的问题是（`归档/phase1-性能优化方案.zip` 内 `phase1-perf-plan.md:81`）记录的缺陷 B4：
「`change_dex_protective` 整 dex RW 且**永不恢复** → 权限位长期暴露」。
Task 1.5 改为页粒度 + 写完恢复。而「恢复 `PROT_READ`」**第一次**需要区分：

- **文件 dex** → 写完**要**恢复只读
- **内存 dex**（Task 1.4，`InMemoryDexClassLoader`）→ buffer 在 native 堆
  （`dpt.cpp:636` `std::unique_ptr<uint8_t[]>`），与相邻分配**共页**，
  恢复只读会把邻居搞崩 → **不能**恢复

错在把这个判断**也**用到了「是否开窗」上。

### 修复

把两个用途拆开（`dpt_hook.cpp`）：

| 决策 | 修复前 | 修复后 |
|---|---|---|
| 是否**开**窗 | `if (restoreRead && ...)` | **无条件**（对内存 dex 不改变权限，heap buffer 本就可写；但每 segment 一次 syscall，且新增「mprotect 失败即放弃本 class」的失败面） |
| 是否**关**窗 | `if (restoreRead)` | 不变（文件 dex 关，内存 dex 不关） |
| 开窗失败回滚 | 无条件回滚 | 加 `if (restoreRead)` —— 只回滚我们改过的权限 |

**这不是回到 v1.0.6**：v1.0.6 是「整 dex 开 + 永不关」；修复后仍是
「页粒度 + 文件 dex 恢复」，**Task 1.5 的安全改进全保留**，只去掉错误的短路。

| | v1.0.6 | v1.0.8（崩） | 修复后 |
|---|---|---|---|
| 开窗范围 | 整 dex | 页粒度 | 页粒度 |
| 是否开窗 | 无条件 | **被误判跳过** ❌ | **无条件** |
| 文件 dex 关窗 | 从不 | 是 | 是 |
| 内存 dex 关窗 | 从不 | 否 | 否 |

### 遗留（v1.0.9 未修，独立问题）

`is_file_dex_location()` 用 `location` 字符串判断**本身不可靠**——日志已证明
文件 dex 会被判成内存 dex。不修时后果退化为「文件 dex 开了窗不关」
（权限暴露，**不崩**，等同 v1.0.6 的 B4 缺陷）。要判准应改用**映射属性**，
例如 `isShellInMemoryDex(begin)` 的地址分支（`begin` 是否落在已注册的
in-memory buffer 范围内），而不是 `location` 字符串。

| 项 | 状态 |
|---|---|
| 根因判定 | **高** —— `restoreRead=0` / `mprotect=-1` / `SEGV_ACCERR` / `loc=Anonymous-DexFile@...jar!` 四个值互相自洽，且与 v1.0.6→v1.0.7 的 diff 完全对应 |
| 诊断能力本身 | **已真机验证**：handler 触发、tombstone 保留 106 帧、`loc=` 未被截断 |
| 修复代码落地 | ✅ 已提交并推送（`ee77871`，v1.0.9） |
| **修复后真机启动** | ✅ **已验证通过**（2026-10-07，Redmi dash / Android 16 / `com.xixin.box`，**默认内存路径**、不带任何参数，冷启动不闪退） |
| CI 编译（`-Wall -Wextra -Werror`） | ⚠ 未确认 —— 本机 arm64 无法编 native（§七），真机 APK 只能出自 CI；但 `gh` CLI 不可用，Actions 页面的编译结论**未经本人核对**。真机通过 ≠ CI 零警告，两者独立 |
| 文件路径 / 多进程 / 多 dex | ⚠ 未验证 |

### 新增教训

1. **一个布尔量不要同时表达两个决策。** `restoreRead` 名字只说了「是否恢复」，
   却被拿去门控「是否开窗」，两者语义相反（不恢复 ≠ 不开），
   崩溃点与判断点隔了 35 行，肉眼 review 极难发现。
2. **用字符串特征判断内存/文件 dex 不可靠。** ART 对两种来源都给出
   `Anonymous-DexFile@<n>.jar!classesN.dex` 形态的 location。判「内存」应看
   映射属性（地址范围 / `mprotect` 是否真改动了权限），不要看路径字符串。
3. **诊断字段要能区分「没做」和「做了但失败」。** `mprotect=-1`（未尝试）与
   `-2`（尝试但失败）分开记，正是这两个值让 v1.0.8 的定位一眼完成；
   若只记一个 `bool ok`，就分不清是漏开窗还是开窗失败。

## 构建类

### 1. `Cannot find directory: shell-files!`

**[本地] 实测**

`dpt.jar` 运行时读不到 `shell-files/`。

**原因**：只跑了 `./gradlew :dpt:jar`（或过时的 `./gradlew assemble`），
没跑完整 build。`shell-files/` 由 `shell/build.gradle` 的 `afterAssembleCopy`
挂在 build 任务的 `doLast` 上生成。

**处理**：`./gradlew build`，且 `dpt.jar` 与 `shell-files/` 必须同次构建
（`build-key` 会校验）。

详见 [构建与发布.md](构建与发布.md#build-key-校验)。

---

### 2. `./gradlew assemble` 产不出完整 `executable/`

**[CI] + [推理]**

`assemble*` 任务不触发 `afterAssembleCopy`（它挂在 `build` 任务上），
只会产出缺少 `shell-files/` 的不完整 `executable/`。

**处理**：一律 `./gradlew build`。README 中英文与 AGENTS.md 均已写此命令
（`088079e` 起；旧版 README 给的 `./gradlew assemble` 已过时）。

### 7. 本地语法检查脚本不可信（重要教训）

**[本地] 实测**

曾在 Termux 上写脚本模拟编译器语法检查来做 Native 改动的"验证"。

## Java / 测试类

### 8. 测试向量凭记忆写错

**[本地] 实测**

ChaCha20 测试最初写成：
- nonce = `000000090000004a00000000`（错）
- Initial Counter = 0（错，应为 1）
- 密文含 `27`（错，应为 `1a`）

**为什么没被发现**：round-trip 测试只验证
"加密后再解密能还原"，任何对称加密都满足，**掩盖了向量本身写错**。

**处理**：从 `https://www.rfc-editor.org/rfc/rfc8439.txt` 抓原文逐字节核对。

**教训**：**标准测试向量必须取自权威原文，不能凭记忆写**，
且 round-trip 测试之外必须有硬编码的期望值。

## 启动性能类（真机实证）

### 22. 加壳的启动开销不在"解密/校验"，而在 dex 结构重组

**[真机] 实测**（2026-10-22）

设备：Redmi `2602BRT18C`，Android 16（SDK 36）。
对照 APK：`app-release-正式版.apk`（未加壳）。
口径：`am force-stop` → 静置 2s → `am start -W`，安装后预热一次并剔除，
每种变体 7 轮背靠背，取 `TotalTime` 中位数。

| 变体 | 打包参数 | 冷启动中位数 | vs 未加壳 |
|---|---|---|---|
| baseline | —（未加壳） | 190 ms | — |
| disk | 默认（落盘加载） | 337 ms | **+147 ms** |
| inmem | `--use-inmemory-dex` | 417 ms | +227 ms |
| plain | `--plain` | 336 ms | +146 ms |

**结论**：`plain`（不抽取指令、dex 完整明文）与默认模式几乎无差别
（336 vs 337 ms）。这说明启动开销**不来自**指令抽取后的运行时解密与类校验。

`inmem` 比 `disk` 慢 80 ms，说明开销也不来自 `xixin_dexes.zip` 的落盘 IO
——`dpt.jar --help` 中"on-disk loading is faster to start"的说法在这台设备上成立。

**推论**：开销来自 dex 结构本身被改变——原多 dex（`classes.dex` 13.9 MB +
`classes3.dex` 7.1 MB）被合并为单个 20.7 MB 壳 dex，业务 dex 以 zip 形式附加
在 `classes.dex` 尾部（`dpt_util.cpp` `readZipLength`/`writeDexAchieve`），
运行时再由 `combineDexElement` 拼入 `DexPathList`。

**因此以下两条曾被提出的优化方向，收益预期为零或未经验证，不要重复投入**：

- hook `art::ClassLinker::VerifyClass` 跳过校验：校验不是开销来源，见 plain 数据。
- 多 dex 化（B 方案）：**未验证**。原推断"可减少 dex element 加载开销"
  没有数据支撑；要验证需用 `-r` 排除规则打出极小壳 dex 再测。

**待验证项**：壳 dex 体积与启动时间是否相关（用 `-r`/`-K` 排除大部分类后对比）。
在拿到该数据前，不要声称多 dex 化有效。

### 23. 壳的启动开销无法通过"让业务 dex 进 AOT"消除

**[真机] 实测**（2026-10-22）

加壳包装包后，系统的 dexopt 档位被降级：

```
加壳版  : arm64 [status=verify]      [reason=install]      base.odex: 16Kb
未加壳  : arm64 [status=speed-profile][reason=baseline]    base.odex: 11251Kb
```

业务 dex 在装包期对 dex2oat 不可见，系统只能做 verify，
之后每次冷启动都现场校验并解释执行。

`ProxyApplication.attachBaseContext` 里的 `BackgroundDexopt`（§24）本意是补偿，
但它**从未生效过**，且有三重独立障碍：

1. **SELinux 拒绝**：`untrusted_app` 无权触碰 `dex2oat_exec`，
   连 `getattr` 都被拒，因此 `pickDex2oat()` 逐个候选都失败并返回 null。
2. **壳自身 hook 了 execve**：`dpt_hook.cpp` 的 `fake_execve` 主动拦截
   含 `dex2oat` 的调用并返回 `EACCES`。
3. **`--compiler-filter=quicken` 已不存在**：Android 14+ 已移除该档位
   （设备上 `grep -c quicken dex2oat64` = 0）。

另外该机制自身还有两处浪费：对十几 MB 的 `xixin_dexes.zip` 计算 SHA-1，
以及一个 5s 延迟线程，全部白做。

**结论**：应用进程内没有任何合法途径为壳 dex 触发 AOT。
这是所有 dex 重组型壳的共同死穴，不是 dpt 的实现缺陷。
若需彻底解决，方向是把保护重心从 dex 移到 native（VMP/Java2C），
代价是包体与编译期，属产品决策而非工程优化。

### 24. `BackgroundDexopt` 在当前 Android 上不可能成功

**[真机] 实测**（2026-10-22）

实测日志（SELinux 直接拒绝，发生在 `getattr` 阶段）：

```
W/dpt-bg-dexopt: avc: denied { getattr } for path="/apex/com.android.art/bin/dex2oat64"
                 scontext=u:r:untrusted_app  tcontext=u:object_r:dex2oat_exec  permissive=0
W/dpt-bg-dexopt: avc: denied { read } for name="dex2oat" tcontext=u:object_r:dex2oat_exec
```

注意 denial 出现在 `getattr`，即 `BackgroundDexopt.pickDex2oat()` 的
`isFile()/canExecute()` 阶段，所以四个候选路径会被逐个否掉、返回 null，
后续逻辑直接跳过。

`run()` 抛出的异常被 `catch (Throwable)` 静默吞掉
（`BackgroundDexopt.java`），因此 Java 层没有任何失败日志，
只有上面两条 avc——排查时容易被误认为"只是偶发失败"。

**结论**：在无 root、目标包不可调试的前提下，此功能不可能成功。
若保留代码，至少应把失败原因打到 log 里，而不是静默跳过；
更合理的做法是直接删除该机制，避免误导后来者以为它有效。

### 25. `ClassLinker::VerifyClass` 在 Android 16 上没有调用者

**[本地] 实测**（2026-10-22，`libart.so` 反汇编）

```
$ nm -D --defined-only libart.so | grep ClassLinker.*VerifyClass
00000000002914d0 T _ZN3art11ClassLinker11VerifyClassEPNS_6ThreadEPNS_8verifier12VerifierDepsENS_6HandleINS_6mirror5ClassEEENS3_15HardFailLogModeE
0000000000218db0 T _ZN3art11ClassLinker23VerifyClassUsingOatFileEPNS_6ThreadERKNS_7DexFileENS_6HandleINS_6mirror5ClassEEERNS_11ClassStatusE
```

对全量反汇编结果统计，`ClassLinker::VerifyClass`（0x2914d0）
**没有任何外部 `bl` 调用者**；686 处相关引用全部指向
`VerifyClassUsingOatFile`（0x218db0）。

**给后续 hook 设计的含义**：要 hook 运行时校验，目标应是
`VerifyClassUsingOatFile`，它直接持有 `DexFile const&`，
可读 `location_` 复用 `is_shell_dex_location()` 做来源判定；
而 `VerifyClass` 的参数里只有 `Handle<mirror::Class>`，拿不到 dex 来源。

**注意**：本节只证明符号与调用关系，**未验证 hook 的可行性与收益**
（收益上限见 §22 的 plain 数据，接近零）。不要依据本节直接开工写 hook。

### 26. arm64 Termux 上 `dpt.jar` 可以正常打包

**[本地] 实测**（2026-10-22）

本文「Native 代码类」记录"aapt2、cmake、NDK clang 全是 x86_64 ELF，本地无法构建"，

实测 `executable/dpt.jar` 在本机（arm64 Termux）可正常完成打包：
