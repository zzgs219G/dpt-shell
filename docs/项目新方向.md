逆向流程 + SO 融合方案

本文档记录两件事：

1. 逆向者视角：从 dpt-shell 加壳 APK 到运行成功的完整攻击路径
2. 防御者视角：dcc + sig_check + dpt-shell 融合为一个 SO 的技术方案

用途：攻防对照，指导后续加固决策。

---

一、逆向流程（攻击者视角）

1.0 总览

```
静态侦察 → 动态脱壳 → DEX 修复 → 入口还原 → 差分分析 → 字符串解密 → 校验绕过 → 重打包
```

每一层都是独立环节，攻击者可以按顺序走，也可以跳过某些环节。

1.1 静态侦察

【输入】目标 APK
【操作】

1. 反编译 AndroidManifest.xml，看 <application> 的 android:name 和 android:appComponentFactory
2. 看 assets/ 目录下的文件名
3. 看 lib/ 目录下有哪些 SO

【识别特征（dpt-shell）】

· android:name="com.luoyesiqiu.shell.ProxyApplication"
· android:appComponentFactory="com.luoyesiqiu.shell.ProxyComponentFactory"
· assets/i11111i111.zip、assets/OoooooOooo、assets/d_shell_data_001
· assets/vwwwwwvwww/ 下多个 .so

【产出】确认是 dpt-shell，记录版本
【成本】30 秒

1.2 动态脱壳

【操作】

1. 把 APK 上传到在线脱壳平台（如 56.al），或用 FART/frida-dexdump 本地跑
2. 让 App 运行，壳的 patchMethod 会把方法体解密写回内存
3. 从进程内存 dump 出已解密的 DEX

【原理】dpt-shell 的 patchMethod 解密后不重新加密，明文常驻内存

【产出】明文 DEX（方法体已还原）
【成本】5 分钟

【关键点】

· 不需要理解 dpt-shell 的加密链
· 不需要找密钥
· 不需要理解 OoooooOooo 格式

1.3 DEX 修复

【操作】

1. 用 MT 管理器"全选修复"
2. 版本号保持原样，闪退则试 038

【原理】dump 出来的 DEX 头部信息（magic、checksum、signature）是坏的，需要重算

【产出】可被 Android 识别的 DEX
【成本】2 分钟

1.4 入口还原

【操作】

1. 从 dump 包附带的 txt 或从壳代码中，找到原始 Application 类名
2. 修改 AndroidManifest.xml 的 android:name
3. 删掉 android:appComponentFactory

【原理】壳用 ProxyApplication 替换了原始 Application，需要换回
【产出】不带壳入口的 APK 骨架
【成本】5 分钟

1.5 差分分析

【操作】

1. 找原始未加固版本（如有），或同类 App
2. 用 jadx/脚本逐类对比
3. 找出被修改的类

【发现】

· 每个 <clinit> 里多了一行 invoke-static 到某个合成本类方法
· 合成本类方法名形如 FlMy（随机 4 字符）
· 方法体是 const-string → toCharArray → xor → forName → getDeclaredMethod → setAccessible → invoke

【成本】5–30 分钟

【anti-diff 干扰】

· 如果你的项目开了 anti-diff，diff 结果会满屏红
· 但类新增和类删除骗不了人：StrDec 是新类，被抽走的方法是 native

1.6 字符串解密

【操作】

1. 看到 const-string 里的加密字符串 + XOR key
2. 用 AI 或脚本批量解密

【还原结果】

```java
Class.forName("com.xixin.box.shell.JniBridge")
     .getDeclaredMethod("clinit", new Class[0])
     .setAccessible(true)
     .invoke(null, new Object[0]);
```

【成本】15 分钟

1.7 校验绕过

【操作】

1. 找到 JniBridge.clinit 声明
2. 去掉 native 关键字
3. 方法体清空成 return-void

```smali
.method public static clinit()V
    .registers 1
    return-void
.end method
```

【原理】DEX 层面删掉 native 关键字，运行时不去 SO 找实现，直接执行空方法体
【产出】签名校验被短路
【成本】5 分钟

1.8 重打包

【操作】

1. apktool b 重打包
2. 用自己密钥签名
3. zipalign 对齐
4. 安装运行

【成本】5 分钟

1.9 全流程成本汇总

环节 时间 工具门槛 备注
静态侦察 30 秒 无 看一眼就知道
动态脱壳 5 分钟 无 56.al 一键
DEX 修复 2 分钟 MT 管理器 全选修复
入口还原 5 分钟 MT 管理器 改 xml
差分分析 5–30 分钟 jadx 对比找注入
字符串解密 15 分钟 AI XOR
校验绕过 5 分钟 MT 管理器 改 smali
重打包 5 分钟 MT 管理器 一键

总计：约 45 分钟，全程无逆向技能要求。

二、SO 融合方案（防御者视角）

2.0 目标

把三个独立组件编译成同一个 SO 文件：

1. dpt-shell 的壳：hook、patchMethod、反调试
2. dcc 抽走的 native 方法：App 运行的代码本体
3. sig_check / env_check：签名校验 + 环境检测

攻击者加载这个 SO = 同时加载全部三个。不加载 = App 没有代码可跑。

2.1 融合后的加载路径

融合前：

```
ProxyApplication → 加载壳 SO → patchMethod 解密 → 解密后方法体里有 loadLibrary("nc")
→ 加载 libnc.so → sig_check constructor 执行
```

融合后：

```
ProxyApplication → 加载 libnc.so（一次加载）
→ constructor 执行：dpt hook 注册 + sig_check 校验 + JNI 方法注册
→ 类加载 → patchMethod 解密 → 解密后方法体里的 loadLibrary("nc") 变 no-op
→ native 方法可用
```

结果：一个 SO、一次加载、一个入口。

2.2 融合的三种效果

效果 说明
不能分工击破 加载 = 全部，不加载 = 全都没有
绕过壳入口变两难 换掉入口 → SO 不加载 → native 方法崩；手动加载 → 签名校验触发 → 崩
符号互相引用 dpt 的函数可调 sig_check，反之亦可；patch 一处会牵连另一处

2.3 三个层次的融合

层次 1：源码目录合并

```
shell/src/main/cpp/
├── dpt/              ← dpt-shell 原有代码
├── dcc/              ← dcc 生成的 native 方法实现
├── sigcheck/         ← sig_check.c + env_check.c + sig_hash.h
├── common/           ← 共用（obfuscate.h、log 等）
└── CMakeLists.txt    ← 一个构建脚本
```

层次 2：constructor 统一调度

```cpp
// 单个 constructor 统一调度，不要依赖多个 constructor 的声明顺序
__attribute__((constructor)) void nc_so_init() {
    nc_init_crypto();      // 先初始化密钥
    nc_init_sigcheck();    // 再执行签名校验
    nc_init_dpt_hook();    // 最后注册 hook
    nc_init_jni();         // 注册 native 方法
}
```

约束：sig_check.c 必须保持 constructor 形式，不能改成 JNI_OnLoad。

· constructor 在 dlopen 时执行
· JNI_OnLoad 在 System.loadLibrary 之后才执行
· 时序安全要求校验必须在 SO 加载瞬间完成

层次 3：JNI 方法注册合并

```cpp
JNIEXPORT jint JNI_OnLoad(JavaVM *vm, void *) {
    JNIEnv *env = nullptr;
    vm->GetEnv((void **) &env, JNI_VERSION_1_6);

    // sig_check 已在 constructor 里跑过，此处不重复
    register_dpt_methods(env);   // dpt 的 JniBridge 方法
    register_nc_methods(env);    // 你的额外 native 方法

    return JNI_VERSION_1_6;
}
```

2.4 五个必须处理的坑

坑 说明 处理
SO 名字 dpt 用的是构建时随机生成的 soName 融合 SO 固定叫 libnc.so，与 DEX 里 loadLibrary("nc") 一致
dpt 的 SO 加密 AndroidPackage.encryptSoFiles 会加密 .bitcode section 融合 SO 要么不加密，要么确保加密部分不冲突
DPT_UNKNOWN_DATA 符号 dpt 会往这个符号写 encKey 融合 SO 不要导出这个符号，或保留专用位置
constructor 顺序 Android 上多个 constructor 顺序不完全可预测 用单个 constructor 统一调度
构建系统不同 dpt 用 CMake，dcc 用 Android.mk 统一用 CMake

2.5 分步执行方案

不要一次性融合，分三步走：

第一步：改名

· 只把 dpt 的 SO 名字改成 libnc.so
· 不改任何逻辑
· 验证：App 能正常跑

第二步：加 sig_check

· 把 sig_check.c 编进 dpt 的 SO
· 让 SO 里多一个 constructor 执行签名校验
· 验证：两个 constructor 共存，App 能跑，签名校验触发

第三步：加 dcc

· 把 dcc 生成的 native 方法也编进来
· 合并 CMakeLists.txt
· 验证：native 方法可用，loadLibrary 变成 no-op

每一步 push 到 GitHub Actions 跑一遍构建，确认编出 SO、能打包、能启动。

2.6 融合后的攻击者路径

```
攻击者绕过 Java 层所有摩擦（字符串加密、anti-diff）
   ↓
发现 Main 类是 native，需要 libnc.so
   ↓
尝试删 SO        →  崩（native 没实现）
尝试不加载 SO    →  崩
尝试手动加载     →  触发 sig_check → 崩
尝试写假 SO      →  需要重写所有 native 方法
尝试 patch 真 SO →  需要逆向，需要 IDA
   ↓
★★★ 无路可走，只能逆向 SO ★★★
```

Java 层所有防御的真正作用不是"拦住"，而是"不提供捷径"。攻击者的终点被唯一化到 SO 逆向。

2.7 SO 层可加固方向（按性价比排序）

加固项 实现方式 成本 效果
strip 符号 -Wl,--strip-all + -fvisibility=hidden 低 IDA 里只看到 sub_XXXX
字符串加密 用项目里已有的 AY_OBFUSCATE 低 关键字符串不出现在二进制
校验逻辑拆散 拆成多个函数，散在不同 .c 文件 中 无法一次性 patch
数据级耦合 校验结果参与 native 方法的运行 中 删掉校验 → native 方法行为错
多个 constructor 有依赖 constructor 之间共享全局状态 中 不能只 patch 一个
OLLVM 控制流平坦化 需引入 LLVM 编译 高 SO 逆向成本数倍增加

前 5 项不需要 IDA 验证，GitHub Actions + Termux readelf 就能确认效果。

四、核心结论

1. Java 层防不住。 jadx/AI 让阅读 Java 几乎无门槛，字符串加密、anti-diff 都是摩擦层，不是防御层。
2. dpt-shell 的结构性弱点是"SO 是可选的"。 攻击者删掉 SO 加载，App 还能跑（方法体是 nop）。
3. 融合方案的结构性优势是"SO 是必需的"。 dcc 抽走的 native 方法在 SO 里，不加载就没有代码。
4. sig_check 和 dcc 融合的意义不是"叠加防御"，而是"让两者互相绑架"。 攻击者动其中任何一个，另一个都会反噬。
5. 最终目标是"逼向 SO"。 Java 层所有防御的真正功能，不是拦住攻击者，而是让所有路径唯一通向 SO 逆向。
6. SO 层加固不需要电脑。 编译参数、字符串加密、逻辑拆散、数据耦合，全部可以 GitHub Actions 验证。
