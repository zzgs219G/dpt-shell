## 四、新旧壳对照（原作者 v2.21.0 口径，补测）

> 本节为 1.6 之后按用户要求补测：汇报口径的主对照从 v1.0.0 换成原作者
> v2.21.0（理由见 §〇 双口径说明）。体积只看默认模式（不测 `-S`）。

### 4.1 方法与披露（先读）

- **素材选择**：运行时对照只能用两壳都能打的 APK。21-dex 的简盒被纯
  v2.21.0 打崩（见 4.3），计算器方案因系统应用数据备份风险被用户否决
  （**计算器全程未动，完好**）→ 最终走**用户签名方案**（用户提议）：
  用户用原始 keystore 手动重签两份加壳包，靠同证书 `install -r` 原地升级。
- **签名验证**：两包证书 SHA-256 `d82e48da…689e` 一致，v2/v3 签名，
  Android 16 安装通过；升级时 `past signatures:[]`（无签名切换的原地升级）。
- **补丁披露**：简盒的 v2.21.0 数据来自 **v2.21.0 + 1 行补丁**
  （`dpt-v221-patched.jar`，见 4.3）——纯 v2.21.0 对简盒无产物（打包即崩）；
  calc 的 v2.21.0 数据为**纯原版**，无需补丁。

### 4.2 体积对照（默认模式，字节）

| APK | 原版 | v2.21.0 | v1.0.9（我们） | 新壳 vs 上游 |
|---|---|---|---|---|
| calc（9.4 MB） | 9,406,820 | 12,934,461（+37.5%） | 13,049,149（+38.7%） | **+114,688 B（+0.89%）** |
| 简盒（28.8 MB） | 28,765,476 | 31,586,945（+9.8%） | 31,730,305（+10.3%） | **+143,360 B（+0.45%）** |

**结论：体积基本持平，新壳比原作者大 0.45%~0.89%。**

### 4.3 大包打包崩溃的根因与补丁（重要发现）

纯 v1.0.0 与纯 v2.21.0 打 `orig-signed.apk`（21 dex）均在**垃圾 dex 合并**处崩溃：

```
Apk.process → AndroidPackage.addJunkCodeDex → DexUtils.mergeDex
→ DexMerger.mergeStringIds → Dex$Section.writeStringData → AssertionError
```

- **根因**：上游 `DexUtils.mergeDex` 写的是 `catch (Exception ignored)`，
  而 `AssertionError` 是 `Error` 不是 `Exception`——接不住，炸穿整个打包。
  上游该方法的注释却写着 "or fails for any other reason, so callers can fall
  back to keeping the dexes separate"——**意图写了，类型写错了**。
- **fork 已修**：commit `5ed1332`（2026-10-05）改为 `catch (Throwable ignored)`。
- **补丁方法**（对对照组的干预，仅本地执行）：git 取 v2.21.0 的 `DexUtils.java`，
  `sed` 改 1 行，`javac --release 11` 编译后 `jar uf` 替换 class →
  `v221/executable/dpt-v221-patched.jar`（原 jar 未动）。
- **结构等价性**：补丁后上游走的就是它自己代码里的 else 分支
  （`addDex` 把垃圾 dex 分离存放），与 v1.0.9 行为相同——两壳打包日志均
  **无** `Merge junk code into classes.dex`（都走了 fallback），垃圾类数
  77（上游）/ 80（我们，每次随机）。产物结构一致，对比公平。

### 4.4 运行时对照（简盒，同会话背靠背）

2026-10-07 16:33（上游）/ 16:35（我们），`bench-runtime.sh` 同协议
（冷启动 10 次 force-stop 取中位数；内存取 bench 后 `dumpsys meminfo <pid>`）：

| 项 | v2.21.0+补丁 | v1.0.9（我们） | 差异 |
|---|---|---|---|
| 冷启动中位数 | **942 ms**（888~1053） | **1,187 ms**（1113~1758） | **+245 ms（+26.0%），我们慢** |
| 冷启动原始样本 | 1035 972 897 889 929 955 888 926 1008 1053 | 1758 1183 1301 1186 1126 1188 1266 1166 1113 1194 | 我们首样本 1758 = `install -r` 后 dexopt 余波，中位数已消化 |
| 热启动 | 0（N/A，Android 16 行为） | 0（N/A） | — |
| 内存 TOTAL PSS | **414,242 K** | **487,872 K** | **+73,630 K（≈72 MB，+17.8%），我们重** |
| code_cache | `i11111i111.zip` 84,227,246 B（**落盘，文件路径**） | 空（**内存路径**） | 结构差异（性能差异的根因线索） |
| 渲染 / 稳定性 | 控制台完整渲染，0 崩溃 | 同 | 平 |

三档链条（原版为 15:25 会话数据，后两档同会话背靠背）：

```
原版无壳   836 ms / 208,897 K
上游壳     942 ms / 414,242 K   （vs 无壳：+106 ms / +205,345 K ≈ 200 MB）
我们      1,187 ms / 487,872 K   （vs 上游：+245 ms / +73,630 K ≈ 72 MB）
```

- **如实结论：运行时（冷启动、内存）两轴新壳均劣于原作者壳。**
  上游走文件路径（首次启动落盘 84 MB zip，后续直接读），我们走内存路径
  （每次进程启动全量载入 21 dex 约 87 MB）——差异方向与 §三 归因一致，
  正是 `phase1-perf-plan.md` 的优化对象。
- 上游壳在 Android 16 的安装/启动/渲染/稳定性与我们**平手**
  （只要过了合并断言这一关，它同样扛得住 21 dex 素材）。
- 打包速度维度反向：**我们比上游快 23.0%**（§2.1）。
- 测量局限（如实）：原版数据来自 15:25 会话（电量 25%），两壳数据来自
  16:33/16:35（电量 11%）；三档非全同会话，链条数值有跨会话成分。
  两壳之间为严格同会话背靠背，是本节主对比。

## 六、结论与遗留

### 6.1 达标统计

| 类别 | 数量 | 明细 |
|---|---|---|
| ✅ 达标 | 7 | 单测、v4 对拍、CI、三条 grep、code_cache、启动稳定性、指令解密（行为代理） |
| ❌ 未达标 | 3 | 打包耗时 −24.7%（目标 −30%）、冷启动增量 +299ms（目标 <150ms）、内存增量 +240MB 级（目标 <5MB） |
| ⚠ 环境替代 | 1 | 本机 `./gradlew build` 不可行，以 CI 绿替代 |
| ⏳ 未测 | 4+ | RW 窗口、mmap 次数、低版本/32 位/AAB 矩阵、指令直读内存 |

### 6.2 重大发现（留给 Phase 2 的问题，本次不修）

1. **内存路径的内存代价未被计划量化**：InMemoryDex 路径让 21-dex 应用的
   TOTAL PSS 从 ~209 MB 涨到 ~504+ MB。计划书 §6.2 的 `<5MB` 目标显然
   按"增量开销"设想，与实测相差两个数量级。需先量化再决策
   （保内存换启动 vs 保启动换内存，或分场景开关）。
2. **冷启动增量 +299ms 超标**：与内存发现同源（启动期集中载入 payload + dex）。
3. **打包提速 −24.7% 未到 −30%**：达成 Task 1.7 的 ≥20% 线，剩余差距需再
   profile（JVM 启动与签名已排除在测量外）。
4. **基线 v1.0.0 在 21-dex APK 上打包崩溃**（`writeStringData` AssertionError）。

### 6.3 待验证（⏳ 随时可补）

- systrace 测 RW 窗口、debug shell 日志数 mmap 次数（均需构建条件）
- 低版本真机（8.0~13）、armeabi-v7a 实跑、AAB 打包运行
- 加壳 APK 关键类的 dex 内存直读（需 root 或可调试进程）
