# 踩坑与故障记录

本文只记录**实际遇到过**的问题。每条都标注证据来源：
- **[本地]** = 在本机（arm64 Termux）实测
- **[CI]** = GitHub Actions 日志实证
- **[推理]** = 读代码推导，未实测
- **[真机]** = 在安卓真机上实测（adb）

---

## 构建类

### 1. `Cannot find directory: shell-files!`

**[本地] 实测**

`dpt.jar` 运行时读不到 `shell-files/`。

**原因**：只跑了 `./gradlew :dpt:jar`（或过时的 `./gradlew assemble`），
没跑完整 build。`shell-files/` 由 `shell/build.gradle` 的 `afterAssembleCopy`
挂在 build 任务的 `doLast` 上生成。

**处理**：`./gradlew build`，且 `dpt.jar` 与 `shell-files/` 必须同次构建
（`build-key` 会校验）。

详见 [构建与发布.md](构建与发布.md#build-key-校验)。

---

### 2. `./gradlew assemble` 产不出完整 `executable/`

**[CI] + [推理]**

`assemble*` 任务不触发 `afterAssembleCopy`（它挂在 `build` 任务上），
只会产出缺少 `shell-files/` 的不完整 `executable/`。

**处理**：一律 `./gradlew build`。README 中英文与 AGENTS.md 均已写此命令
（`088079e` 起；旧版 README 给的 `./gradlew assemble` 已过时）。

---

### 3. `cannot execute binary file` —— x86_64 工具链跑在 arm64 上

**[本地] 实测**

本机是 arm64 Termux，而 aapt2、SDK cmake 3.31.1、NDK clang 全是 **x86_64 ELF**：

```
AAPT2 aapt2-8.10.0-12782657-linux Daemon #0: Daemon startup failed
```

**处理**：不要试图绕过。这是环境限制，走 CI 验证。

---

### 4. Termux 的 cmake 不可用

**[本地] 实测**

Termux `cmake` 4.4.4 缺符号，无法运行。

**处理**：同上，走 CI。

---

### 5. NDK 目录名与 AGP 期望不一致

**[本地] 实测**

AGP 硬编码期望 `27.0.12077973`。若解压 NDK 后目录名是
`android-ndk-r27c`，构建直接失败。

**处理**：重命名目录为 `27.0.12077973`。
（改名的过程中曾把目录搞成套娃并误删，只能从压缩包重新解压恢复 ——
**改名前先备份**。）

---

### 6. submodule 未初始化导致 Native 编译失败

**[本地] + [CI]**

`git clone` 不带 `--recursive` 时，4 个 vendored 库都是空目录。

**处理**：

```bash
git submodule update --init --recursive
```

---

### 7. 本地语法检查脚本不可信（重要教训）

**[本地] 实测**

曾在 Termux 上写脚本模拟编译器语法检查来做 Native 改动的"验证"。
**问题**：该脚本在**完全未修改的基线文件上也会报错**。

**结论**：这类自制工具会产出"能跑但结论错误"的结果，**比没有更危险**。

**正确做法**：Native 改动靠
1. 本地代码审查 + 逻辑推导（对齐现有风格、头文件包含、宏用法）
2. `git push` 后由 CI 跑真实编译
3. **读 CI 日志**判断，而不是只看绿灯

CI 用 `-Wall -Wextra -Werror`，比自制脚本严格得多。

## Java / 测试类

### 8. 测试向量凭记忆写错

**[本地] 实测**

ChaCha20 测试最初写成：
- nonce = `000000090000004a00000000`（错）
- Initial Counter = 0（错，应为 1）
- 密文含 `27`（错，应为 `1a`）

**为什么没被发现**：round-trip 测试只验证
"加密后再解密能还原"，任何对称加密都满足，**掩盖了向量本身写错**。

**处理**：从 `https://www.rfc-editor.org/rfc/rfc8439.txt` 抓原文逐字节核对。

**教训**：**标准测试向量必须取自权威原文，不能凭记忆写**，
且 round-trip 测试之外必须有硬编码的期望值。

### 9. JUnit 断言用错

**[本地] 实测**

`java.util.Arrays.equals(byte[], String)` 无匹配重载，编译失败。

**处理**：数组比较用 `java.util.Arrays.equals(byte[], byte[])`。

`dpt/build.gradle` 的 JUnit 依赖用了动态版本 `4.+`，需要联网解析。

## Native 代码类（CI 实证）

### 12. `MultiDexCode.h` 缺类结尾 `;`

**[CI] 实测**

修改该文件时误删了命名空间闭合括号，且当时补 `;` 的操作有误。

**CI 报错**：

```
dpt_hook.cpp:560:2: error: expected '}'
note: to match this '{'  MultiDexCode.h:33 namespace dpt::data {
```

**处理**：文件结尾补回 `};`（类闭合）+ `}`（命名空间闭合）。

---

### 13. 构造函数定义缺少限定符

**[CI] 实测**

```cpp
MultiDexCode::MultiDexCode() { ... }   // 错
```

在 `namespace dpt::data` 外的 `.cpp` 里这样定义会报未声明标识符。

**CI 报错**：

```
dpt_hook.cpp: MultiDexCode.cpp:13:1: error: use of undeclared identifier 'MultiDexCode'
```

**处理**：写成 `dpt::data::MultiDexCode::MultiDexCode()`。

### 14. CI 的 warning 噪音

**[CI] 实测**

一次成功的构建有 68 个 warning，**全部来自 vendored Dobby**，
项目自己的改动文件零 warning（CI 用 `-Wall -Wextra -Werror`）。

**识别**：看 warning 来自哪个文件，别被 vendored 库的噪音误导。

## CI / 发布类

### 15. tag 不符合 semver 被拒

**[CI] 实测**

用 `v1.0` 打 tag，发布失败：

```
The parameter "automatic_release_tag" was not set and the current tag
"v1.0" does not appear to conform to semantic versioning.
```

**处理**：用 `vX.Y.Z` 三段格式，如 `v1.0.0`。

---

### 16. Release 创建被拒：缺 `contents: write`

**[CI] 实测**

构建和 zip 都成功了，卡在最后一步：

```
Resource not accessible by integration
```

**原因**：`release.yml` 的 job 未声明 `permissions`，
`GITHUB_TOKEN` 沿用仓库默认权限，没有 `contents: write`。

**处理**：在 `release.yml` 的 job 下加：

```yaml
permissions:
  contents: write
```

**注意**：这类问题**不会**在本地复现，只有 CI 才暴露。

---

### 17. 本地遗留 tag 挡住新版本号

**[本地] 实测**

克隆仓库时带下一个从未推送的本地 tag `v1.0.0`（指向 2022 年的游离 commit），
导致 `git tag v1.0.0` 报 `already exists`。

**处理**：`git ls-remote --tags origin` 确认远端是否存在。
本地游离 tag 可直接 `git tag -d`。

---

### 18. 改 commit message 需要重写历史

**[本地] 实测**

误加 `Co-Authored-By` trailer 后想清除：

```bash
FILTER_BRANCH_SQUELCH_WARNING=1 git filter-branch -f \
  --msg-filter "sed '/^[[:space:]]*Co-Authored-By: Claude/d'" \
  <earliest>~1..HEAD
```

**注意**：
- 需要 `git push --force-with-lease`（**不要**用 `--force`，
  前者会校验远端是否被别人更新过）
- 已发布的 tag 和 Release 会与新 commit 脱节，需删掉重发
- 重写前先建备份分支：`git branch backup <old-head>`
- filter-branch 失败时**会自动回滚**，可安全重试
- 本环境**没有 `perl`**，只能用 `sed`

### 19. GitHub API 匿名调用被限流

**[本地] 实测**

未认证访问 Actions API 返回 403（rate limit）。

**处理**：从 git credential 里取 token：

printf 'protocol=https\nhost=github.com\n\n' | git credential fill

**不要提交进仓库**。

## 方法论

### 20. 不要伪造验证结论

**[本地] + [推理]**

无法验证的项目（无 adb 设备、真机行为）必须明确标注**"待验证"**，
不能给出估算数字冒充实测结果。

**分层原则**：

| 层 | 手段 |
|---|---|
| Java 代码 | JUnit 单测（本地可跑） |
| Native 代码 | GitHub Actions 真实编译 |
| 真机行为 | adb 设备（无设备则标注待验证） |
| 性能数据 | 真实构建产物上测，不能估算 |

## 启动性能类（真机实证）

### 22. 加壳的启动开销不在"解密/校验"，而在 dex 结构重组

**[真机] 实测**（2026-10-22）

设备：Redmi `2602BRT18C`，Android 16（SDK 36）。
对照 APK：`app-release-正式版.apk`（未加壳）。
口径：`am force-stop` → 静置 2s → `am start -W`，安装后预热一次并剔除，
每种变体 7 轮背靠背，取 `TotalTime` 中位数。

| 变体 | 打包参数 | 冷启动中位数 | vs 未加壳 |
|---|---|---|---|
| baseline | —（未加壳） | 190 ms | — |
| disk | 默认（落盘加载） | 337 ms | **+147 ms** |
| inmem | `--use-inmemory-dex` | 417 ms | +227 ms |
| plain | `--plain` | 336 ms | +146 ms |

**结论**：`plain`（不抽取指令、dex 完整明文）与默认模式几乎无差别
（336 vs 337 ms）。这说明启动开销**不来自**指令抽取后的运行时解密与类校验。

`inmem` 比 `disk` 慢 80 ms，说明开销也不来自 `xixin_dexes.zip` 的落盘 IO
——`dpt.jar --help` 中"on-disk loading is faster to start"的说法在这台设备上成立。

**推论**：开销来自 dex 结构本身被改变——原多 dex（`classes.dex` 13.9 MB +
`classes3.dex` 7.1 MB）被合并为单个 20.7 MB 壳 dex，业务 dex 以 zip 形式附加
在 `classes.dex` 尾部（`dpt_util.cpp` `readZipLength`/`writeDexAchieve`），
运行时再由 `combineDexElement` 拼入 `DexPathList`。

**因此以下两条曾被提出的优化方向，收益预期为零或未经验证，不要重复投入**：

- hook `art::ClassLinker::VerifyClass` 跳过校验：校验不是开销来源，见 plain 数据。
- 多 dex 化（B 方案）：**未验证**。原推断"可减少 dex element 加载开销"
  没有数据支撑；要验证需用 `-r` 排除规则打出极小壳 dex 再测。

**待验证项**：壳 dex 体积与启动时间是否相关（用 `-r`/`-K` 排除大部分类后对比）。
在拿到该数据前，不要声称多 dex 化有效。

### 23. 壳的启动开销无法通过"让业务 dex 进 AOT"消除

**[真机] 实测**（2026-10-22）

加壳包装包后，系统的 dexopt 档位被降级：

```
加壳版  : arm64 [status=verify]      [reason=install]      base.odex: 16Kb
未加壳  : arm64 [status=speed-profile][reason=baseline]    base.odex: 11251Kb
```

业务 dex 在装包期对 dex2oat 不可见，系统只能做 verify，
之后每次冷启动都现场校验并解释执行。

`ProxyApplication.attachBaseContext` 里的 `BackgroundDexopt`（§24）本意是补偿，
但它**从未生效过**，且有三重独立障碍：

1. **SELinux 拒绝**：`untrusted_app` 无权触碰 `dex2oat_exec`，
   连 `getattr` 都被拒，因此 `pickDex2oat()` 逐个候选都失败并返回 null。
2. **壳自身 hook 了 execve**：`dpt_hook.cpp` 的 `fake_execve` 主动拦截
   含 `dex2oat` 的调用并返回 `EACCES`。
3. **`--compiler-filter=quicken` 已不存在**：Android 14+ 已移除该档位
   （设备上 `grep -c quicken dex2oat64` = 0）。

另外该机制自身还有两处浪费：对十几 MB 的 `xixin_dexes.zip` 计算 SHA-1，
以及一个 5s 延迟线程，全部白做。

**结论**：应用进程内没有任何合法途径为壳 dex 触发 AOT。
这是所有 dex 重组型壳的共同死穴，不是 dpt 的实现缺陷。
若需彻底解决，方向是把保护重心从 dex 移到 native（VMP/Java2C），
代价是包体与编译期，属产品决策而非工程优化。

### 24. `BackgroundDexopt` 在当前 Android 上不可能成功

**[真机] 实测**（2026-10-22）

实测日志（SELinux 直接拒绝，发生在 `getattr` 阶段）：

```
W/dpt-bg-dexopt: avc: denied { getattr } for path="/apex/com.android.art/bin/dex2oat64"
                 scontext=u:r:untrusted_app  tcontext=u:object_r:dex2oat_exec  permissive=0
W/dpt-bg-dexopt: avc: denied { read } for name="dex2oat" tcontext=u:object_r:dex2oat_exec
```

注意 denial 出现在 `getattr`，即 `BackgroundDexopt.pickDex2oat()` 的
`isFile()/canExecute()` 阶段，所以四个候选路径会被逐个否掉、返回 null，
后续逻辑直接跳过。

`run()` 抛出的异常被 `catch (Throwable)` 静默吞掉
（`BackgroundDexopt.java`），因此 Java 层没有任何失败日志，
只有上面两条 avc——排查时容易被误认为"只是偶发失败"。

**结论**：在无 root、目标包不可调试的前提下，此功能不可能成功。
若保留代码，至少应把失败原因打到 log 里，而不是静默跳过；
更合理的做法是直接删除该机制，避免误导后来者以为它有效。

### 25. `ClassLinker::VerifyClass` 在 Android 16 上没有调用者

**[本地] 实测**（2026-10-22，`libart.so` 反汇编）

```
$ nm -D --defined-only libart.so | grep ClassLinker.*VerifyClass
00000000002914d0 T _ZN3art11ClassLinker11VerifyClassEPNS_6ThreadEPNS_8verifier12VerifierDepsENS_6HandleINS_6mirror5ClassEEENS3_15HardFailLogModeE
0000000000218db0 T _ZN3art11ClassLinker23VerifyClassUsingOatFileEPNS_6ThreadERKNS_7DexFileENS_6HandleINS_6mirror5ClassEEERNS_11ClassStatusE
```

对全量反汇编结果统计，`ClassLinker::VerifyClass`（0x2914d0）
**没有任何外部 `bl` 调用者**；686 处相关引用全部指向
`VerifyClassUsingOatFile`（0x218db0）。

**给后续 hook 设计的含义**：要 hook 运行时校验，目标应是
`VerifyClassUsingOatFile`，它直接持有 `DexFile const&`，
可读 `location_` 复用 `is_shell_dex_location()` 做来源判定；
而 `VerifyClass` 的参数里只有 `Handle<mirror::Class>`，拿不到 dex 来源。

**注意**：本节只证明符号与调用关系，**未验证 hook 的可行性与收益**
（收益上限见 §22 的 plain 数据，接近零）。不要依据本节直接开工写 hook。

### 26. arm64 Termux 上 `dpt.jar` 可以正常打包

**[本地] 实测**（2026-10-22）

`踩坑记录.md` §3 记录"aapt2、cmake、NDK clang 全是 x86_64 ELF，本地无法构建"，
该结论**只适用于 Gradle/Native 构建**。

实测 `executable/dpt.jar` 在本机（arm64 Termux）可正常完成打包：

```
java -jar executable/dpt.jar -f orig.apk -o out_disk.apk      # 成功，9.46 MB
java -jar executable/dpt.jar -f orig.apk -o out_plain.apk --plain        # 成功，8.97 MB
java -jar executable/dpt.jar -f orig.apk -o out_inmem.apk --use-inmemory-dex  # 成功，9.46 MB
```

**含义**：需要真机对照实验时，**不必走 CI**，本机即可产出对照 APK。
§3 的"走 CI 验证"仅针对 shell 模块的 native 编译。
