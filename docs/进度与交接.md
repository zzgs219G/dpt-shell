### 4.1 目标与最终方案（SPLICE）

打包时不把受保护 dex 写进 `code_cache/`，运行时从 `classes.dex` 内嵌 zip 直接读出，
交给 `InMemoryDexClassLoader(ByteBuffer[], parent)`，再把它的 dexElements **追加**
到应用的 DexPathList（splice）。zip 全程不落盘。

关键决策：**分支全部放在 native `combineDexElements` 内部，Java shell 零改动。**

```
cbde(cl)                                 ← 3 个调用点全部保持原样
  └─ combineDexElements (native)
       ├─ g_use_in_memory_dex?
       │    ├─ yes → combineInMemoryDexElements()   ← 内存路径
       │    │         失败? → 落盘回退(写 zip) → 走文件路径
       │    └─ no  → getCompressedDexesPath + combineDexElement(文件路径)
       └─ junkCodeDexProtect()                      ← 两条路径都执行(只 FindClass，不读 zip)
```

模式开关 `g_use_in_memory_dex` 在 `read_shell_config`（JNI_OnLoad，先于一切 ia/cbde）
里一次性决定：

```cpp
g_use_in_memory_dex = !g_shell_config.disable_inmemory_dex
        && android_get_device_api_level() >= __ANDROID_API_Q__;   // 必须 ≥29
```

- API < 29：location 不含 multidex 下标（26–28 是 `Anonymous-DexFile@addr-addr`），
  多 dex 全被解析成 dex0 → 必须走文件路径。
- 配置解析失败 / 早退：flag 保持 false = 安全的文件路径。
- `init_app` 按 flag 跳过 `extractDexesInNeeded`；`junkCodeDexProtect` 不受影响
  （它是 `FindClass`，不读 zip；keep dex 仍是文件元素，junk 类仍可被找到）。

#### 内存路径（`combineInMemoryDexElements`）

1. `ensure_package_loaded`（复用 Task 1.8 的 mmap 缓存）→ `read_zip_file_entry("classes.dex")`
   → `readZipLength` 切出内嵌 zip（`[dex… | zip | u32be len]`，与 `writeDexAchieve` 同源逻辑）。
2. minizip 内存流遍历 zip（**必须 `mz_stream_open`**，与 `read_zip_file_entry` 模式一致；
   实施时漏掉过一次，会导致永远打开失败、静默走文件路径）。
3. entry 名 → `in_memory_dex_number`（镜像打包侧 `DexUtils.getDexNumber`：
   `classes.dex`→0、`classesN.dex`→N-1、其他→-1）。任何非 `classesN.dex` 的 entry
   （如 junkcode.dex）→ 整体放弃 → 回退文件路径。
4. 编号必须连续 `0..n-1`（否则回退）——数组位置 = payload dexIdx，
   ART 按 buffer 在 `ByteBuffer[]` 中的位置派生运行时 multidex 后缀。
5. 每个 dex `new` 出堆缓冲 → `NewDirectByteBuffer` → 组 `ByteBuffer[]`。
6. `jni::NewObject` 构造 `InMemoryDexClassLoader(buffers, targetClassLoader)`
   （`GetMethodID` 失败时 jni 辅助函数不清理异常，调用点后补一次 `ExceptionCheck+Clear`）。
7. `NewGlobalRef` 保活 loader；`unique_ptr.release()` 让缓冲**永不释放**
   （ART 的 NonOwningMemoryRegion 引用原缓冲，且 buffer 内存 + elements 必须活到进程结束）。
   NewGlobalRef 失败（OOM）→ 在 release 之前 return false，回退时 unique_ptr 正常析构。
8. `registerShellInMemoryDex(begin, size)` 登记地址范围（供 dpt_hook 白名单）。
9. 反射取临时 loader 的 `pathList.dexElements`，与文件路径 `combineDexElement`
   完全同构的方式 append 进目标 PathClassLoader。
   **所有 `return false` 都发生在 `setDexElements` 之前**，不存在"半次 splice"。

#### 回落（`combineDexElements` 内）

```cpp
if (g_use_in_memory_dex && !combineInMemoryDexElements(...)) {
    g_use_in_memory_dex = false;
    锁 g_write_dexes_mutex → ensure_package_loaded → extractDexesInNeeded → release;
}
if (!g_use_in_memory_dex) { …原文件路径… }
junkCodeDexProtect(env);   // 无条件
```

#### patchClass 侧配套（dpt_hook.cpp）

- `is_shell_dex_location(location, begin)`：location 含 `i11111i111.zip`
  **或**（含 `Anonymous-DexFile` 前缀 **且** `isShellInMemoryDex(begin)`）。
  ART 给**所有**内存 dex（含应用自己的 InMemoryDexClassLoader）统一
  `Anonymous-DexFile` 前缀，必须用登记范围白名单防误伤。
- `dexMemMap` 从 dex 下标键改为**映射地址键**（`std::set<uint8_t*>`）：
  文件 dex 和内存 dex 都可能解析成下标 0，按下标共享 memo 会让其中一个
  永远不被 mprotect → 恢复指令时 SIGSEGV。
- `findClassIndex` 提到 `change_dex_protective`(mprotect) **之前**：
  不在 payload 里的 dex（keep dex 等）零副作用——不 mprotect、不写。
  副作用：这些 dex 也不再进 mprotect memo（本来就不该进）。

### 4.2 与计划书的偏差（§4.3.7）

| 计划书 | 实际 | 理由 |
|---|---|---|
| Java 侧造 factory 返回 wrapper loader | **Java 零改动**，native cbde 内 splice | 少改一个语言层；cbde 调用点语义不变 |
| ShellConfig 加 `useInMemoryDex` 运行时字段 | 只有 `disable_inmemory_dex`（打包开关），运行时用 native `g_use_in_memory_dex` | 运行时 flag 不进 JSON |
| in-memory 分支跳过 junk 校验 | **不跳过**，junk 校验无条件执行 | junkCodeDexProtect 只 FindClass，与 zip 无关 |
| 放宽 location 判断即可 | 放宽 + **地址白名单** + dexMemMap 改键 + findClassIndex 前移 | 防止误 patch 陌生内存 dex；防 mprotect memo 撞键 |
| — | 额外：编号连续性校验、entry 名异常整体回退 | 位置错位=错误 payload 恢复，宁可降级 |

CLI（**§13 已反转，以下为 Task 1.4 当时的契约**）：`--disable-inmemory-dex`
（`Const.OPTION_DISABLE_INMEMORY_DEX_LONG`），打包配置 JSON 同名字段
`disable_inmemory_dex`。当时两者**只能强制关，不能开**；§13 后默认即磁盘，
改为 `--use-inmemory-dex` / `use_inmemory_dex`（只能强制开）。
`Apk.protect()`：`super.protect()` 合并 CLI → `process()` → `writeConfig()`，
顺序保证 CLI 开关最终进入内嵌配置（`ShellConfig.toJson()` 已 put）。

### 4.3 回退矩阵（每一格都要能工作）

| 场景 | 行为 |
|---|---|
| **默认（任何 API）** | **文件路径（磁盘加载）** ← §13 反转后的默认 |
| `--use-inmemory-dex` 或配置 `use_inmemory_dex:true`，且 API ≥ 29 | 内存路径 |
| `--use-inmemory-dex` 但 API 26–28 / <26 | 文件路径（flag=false） |
| `--disable-inmemory-dex`（已废弃 no-op） | 文件路径（同默认） |
| 配置解析失败/早退 | 文件路径（flag 保持 false） |
| classes.dex 缺失 / zip 长度字段坏 | 内存失败 → 落盘回退 → 文件路径 |
| zip 里出现非 `classesN.dex` entry（如 junkcode.dex 合并失败时） | 同上 |
| 编号不连续（缺 classesN） | 同上 |
| `InMemoryDexClassLoader` 构造抛异常（JNI 层失败） | 同上 |
| NewGlobalRef OOM | 同上（release 前失败，缓冲正常释放） |
| 回落后第二次 cbde（理论不会发生，有 `sIsReplacedClassLoader` 挡） | 文件路径幂等由 `extractDexesInNeeded` 的 access 检查保证 |

`cbde` 每进程至多执行一次：3 个调用点里 `instantiateApplication`、`attachBaseContext`
受 `Global.sIsReplacedClassLoader` 守卫，`instantiateClassLoader` 先跑并置位
（Android 10+ 时它先于另外两个）。这与文件路径本来就依赖的前提一致。

## 8. Task 1.5 设计要点（已读 `phase1-perf-plan.md` §5，开工前重读原文）

- 现状 `change_dex_protective`：整 dex RW 且**永不恢复** → 改为
  **每类一次**：收集本类 insns 页 → `std::set` 排序去重 → 按页取锁（防死锁）
  → 分段连续化后 `dpt_mprotect` RW → 逐方法解密 → 恢复 READ → 解锁。
- 三个已知错误别再犯：❌ `dpt_mprotect(first,last)` 覆盖无关页（要分段）；
  ❌ 页锁表只增不减（可接受但要文档标注）；❌ 自己算页对齐
  （`dpt_mprotect` 内部已用 `DPT_PAGE_START` 对齐）。
- **恢复 READ 前必须 `__builtin___clear_cache(segStart, segEnd)`**（ARM64 i-cache）。
- 删除：`change_dex_protective`、`dexMemMap`。
- 新增：`dpt_util.h` 声明 `g_pageLocks` / `getPageLock`。
- ⚠ 未定稿风险：in-memory dex 底层是 malloc/direct buffer，恢复 PROT_READ
  可能殃及同页邻居 → 可能要对 in-memory dex 跳过 mprotect（buffer 本就 RW），仅留页锁。

### 1.5 实施前设计决策（2026-10-06 会话，压缩前固化）

1. **in-memory dex 跳过 mprotect（定稿）**：内存 dex 底层是 `new` 堆缓冲
   （Task 1.4 §4.1 第 5 步），页边界与 malloc 邻居共享。恢复 PROT_READ
   会把同页邻居也变只读 → 其他线程写邻居即 SIGSEGV；且 buffer 本就 RW，
   mprotect RW 是多余系统调用。**方案**：仅文件 dex（location 含
   `i11111i111.zip`）做 RW→READ 切换；内存 dex 只取页锁 + 写回 +
   clear_cache，不动权限。
2. **段失败全或无**：任一段 mprotect RW 失败 → 恢复已设 RW 的段 →
   解锁 return + ELOG，不写任何方法（避免半解密状态）。
3. **clear_cache 位置**：写回后、恢复 READ 前，按段刷
   `__builtin___clear_cache(segStart, segEnd)`；内存 dex 也要刷
   （写的是热指令，不刷仍执行密文）。
4. **patchClass 改造**：`patchOneClassMethod`（:289-323）改为收集器模式
   （`PendingPatch{methodIdx, codeOff, enc, insnsSize}` + `touchedPages`），
   patchClass 统一取锁/写回/恢复。现有 class_data 解析（:404-441 内联
   new 数组）保留不动。
5. **删除**：`change_dex_protective`（:158-176）、`dexMemMap`（:24）。
6. **页锁表**：`dpt_util.h` 声明 `g_pageLocks`/`g_pageLockTableMutex`/
   `getPageLock`，`dpt_hook.cpp` 定义（计划书 §5.4）。

### 8.1 落地偏差（与计划书 §5.5 伪码不同之处）

| 计划书 §5.5 | 实际落地 | 理由 |
|---|---|---|
| `std::set<uintptr_t> touchedPages` | 同（保留） | 去重+排序，锁与分段都依赖 |
| 每段 `dpt_mprotect` 不看返回值 | **检查返回值 + 段失败全或无** | §8 决策 2；失败回滚已开段，整类不写 |
| 页集合用 `realInsns` 推导 | `collectTouchedPages`，末页由**最后一字节**推导 | 计划书用 `DPT_PAGE_START(realInsns+len-1)+pageSize`，等价且更直观；`len==0` 已提前挡掉，无下溢 |
| 所有 dex 都做 RW→READ | **仅文件 dex**（`is_file_dex_location`） | §8 决策 1：内存 dex 跳过 mprotect |
| `__builtin___clear_cache` 只在恢复前 | 同，**两条路径都刷**（内存 dex 也刷） | 写的是热指令，不刷仍执行密文 |
| 计划书伪码 `m.methodIdx` / `m.codeOff` | 实际字段 `method_idx_delta_` / `code_off_` | 对齐 `dex_file.h` 的 `ClassDataMethod` |
| `patchMethodInsns` 内联在 patchClass | 保留 `patchMethodInsns` 函数（写回+解密），另加 `collectOneClassMethod` 收集 | 收集与写回分离，写回逻辑零改动，降低回退风险 |

另：`dpt_hook.cpp` 顶部 `<set>` 保留，新增 `<cstdint>/<iterator>/<memory>/<mutex>/
<unordered_map>/<utility>/<vector>`。

### 8.2 Task 1.5 实施记录（2026-10-06 会话）

**改动文件**：`shell/src/main/cpp/dpt_hook.cpp`、`shell/src/main/cpp/dpt_util.h`
（`dpt.cpp` **未改**——计划书 §5.6 说的 `dexMap` 在 Task 1.1 已删除，实测 `grep dexMap` 无命中）。

**结构**：

```
patchClass(class)
  ├─ junk 检查 / location 门槛 / findClassIndex（不变）
  ├─ 收集阶段：collectOneClassMethod × (direct+virtual)
  │    ├─ 载荷配对校验（encryptedInsns==null / methodIdx 不匹配 → 跳过，同旧逻辑）
  │    ├─ patches.push_back(PendingPatch{methodIdx, codeOff, enc, insnsSize})
  │    └─ collectTouchedPages(insns_, insnsSize) → touchedPages
  └─ 执行阶段（patches 非空时）
       ├─ 按页序取 g_pageLocks（unique_lock 向量，逆序自动解锁）
       ├─ touchedPages 合并成连续段 → 逐段 mprotect RW（仅文件 dex）
       │    失败 → 回滚已开段 → 整类不写（全或无）
       ├─ 逐 patch patchMethodInsns（解密写回，逻辑未改）
       ├─ 逐段 __builtin___clear_cache（两条路径都刷）
       └─ 仅文件 dex：逐段 mprotect PROT_READ 恢复
```

**与旧行为的差别**：旧版 `change_dex_protective` 把**整 dex** 设 RW 且**永不恢复**；
新版只对**本类方法触及的页**开 RW 窗口，写完即恢复 READ。权限暴露面从
"整 dex 整个进程生命周期"缩到"几页 × 一个类的解密耗时"。

**未做（有意）**：`patchClass` 里 `dexSize` 变量仍用于 `begin==nullptr||dexSize==0`
的守卫，但不再传给任何 mprotect；`is_file_dex_location` 只看 location，
不用 `dexSize`——与 §8 决策 1 一致。

**验证状态**：代码已入库（`a35b3e1`，随 v1.0.7 发布）。本机 arm64 跑不了 NDK
工具链（AGENTS.md §6），落地时只做了逐行代码审查 + 括号/符号静态核对；
**编译与真机的直接确认缺失**——但该代码在 v1.0.8 真机崩溃中**确实运行过**
（崩溃点即 `patchMethodInsns`，见 §11.6），v1.0.9 修复后真机通过。见 §8.3。

  （列一个不存在的路径可能让 release action 整体失败，与非致命意图相悖）

- **为什么必须随 Release 存**：`soName` 每次构建随机重生成（根 `build.gradle`），

### 11.2 SIGSEGV / SIGBUS handler

- `dpt_hook.cpp`：`dpt_install_crash_handler()` + `dpt_crash_handler()`
- `dpt.cpp`：`init_dpt()` 里在 **`dpt_hook()` 之前**调用（即 `bytehook_init()` 之前）
- 诊断变量（`thread_local` POD，非 `std::string` —— handler 里不能碰堆）：
  `g_last_location` / `g_last_restore_read` / `g_last_mprotect` / `g_last_method_idx`
- 输出一行 `ANDROID_LOG_FATAL`，TAG = `dpt_native`：
  `SIG11 addr=0x... code=2 loc=Anonymous-DexFile... restoreRead=0 mprotect=-1 methodIdx=...`
- 取日志：`adb logcat -b main -s dpt_native`（FATAL 级，和 `ELOG` 同通道）

### 11.3 关键设计决策（不要改回去）

1. **转发 prev handler，不用 `_exit()`**。`docs/crash.log`（v1.0.8）就是 debuggerd 的
   tombstone；`_exit()` 会让 debuggerd 不介入，**拿日志换掉了整份现场**，亏。
   handler 打完日志后转发给 `sigaction` 保存的 `prev`。`SIG_DFL` 分支用
   `syscall(__NR_tgkill, ...)` 而非 `kill(pid,...)`，避免信号投递到别的线程、
   tombstone 记错 tid。
2. **handler 必须装在 `bytehook_init()` 之前**。bhook 自己也装 SIGSEGV/SIGBUS
   （`bh_core.c:94` `bytesig_init`），且它用 `dlsym(libc)` 绕过 ART sigchain 直接
   写内核槽位（`bytesig.c:bytesig_real_sigaction`）。装在我们之前 → bhook 在最外层，
   只在**它不消费**的真崩溃时转发给我们，`BYTESIG_TRY` 保护不受影响。装反了会
   截断 bhook 的保护读。
3. **`g_last_mprotect` 语义**（修复后）：`0` = **尝试开窗**（不是「已打开」——
   该赋值发生在第一个 `mprotect` 之前，中间崩溃仍会报 `0`）；开窗阶段为 `0`，
   文件 dex 随后在收尾时被置 `1`（内存 dex 停在 `0`，因为不关窗）；
   `1` = 正在/已经关闭（`restore` 之前赋值，同 `0` 的口径：赋值早于动作）；
   `-2` = 尝试开窗但失败；`-3` = 恢复 `PROT_READ` 失败；`-1` = 未尝试开窗
   （现在只在 `dpt_install_crash_handler` 的预写里出现，正常流程不会再有）。
   修复前 `-1` 表示「内存 dex，`restoreRead=false` 短路掉了开窗」，**那正是
   v1.0.8 崩溃的特征**——一眼说明「RW 窗口从未打开」。
4. **只写 logcat，不写文件**。`write(2)` 在 Android app 进程里重定向到
   `/dev/null`，看不到；`/data/local/tmp` 实测 app 无写权限（`shell:shell 771`，
   others 无 `w` 位）；`/data/data/<pkg>/` 的 release 包 `adb pull` 需要 root。
   崩溃只打两行，main buffer 几 MB 冲不掉，不值得为文件权限再折腾。
   注：`__android_log_write` 严格说不是 POSIX async-signal-safe，这是**知情取舍**
   （换来的是日志真的能被看到），已在代码注释里写明。
5. **诊断变量是 `thread_local` POD，不是 `std::string`**；但**重入守卫
   `g_in_crash_handler` 是普通全局**——它首次写入发生在 handler 内部，若用
   `thread_local`，没跑过 `patchClass` 的线程会在信号上下文里触发 TLS 分配
   （bionic 对 dlopen 模块走 `__tls_get_addr` → `calloc`）。
   `dpt_install_crash_handler()` 里对 4 个诊断变量做一次预写，**只覆盖安装线程**；
   跑过 `patchClass` 的其他线程同样安全（那些变量已被写过）。**残余缺口**：
   在 SO 加载前就存在、且从未跑过 `patchClass` 的线程发生崩溃时，仍可能在 handler
   里触发 TLS 分配。已接受此风险（诊断用途，不影响业务）。
   另注：`g_last_method_idx` 记的是该类**第一个**被收集的方法，不一定是崩溃时正在
   打补丁的那个。

### 11.4 已知风险与有意不采纳的建议（评审后留档）

独立 review 提了两条**未采纳**的建议，理由如下（下一任若要改，先读这段）：

1. **不用 `dlsym` 真 `sigaction` 装 handler**。review 建议学 bhook
   （`bytesig.c:115`）绕过 sigchain。**不采纳**：那会让我们的 handler 占据
   **内核槽位**、shadow 掉 ART 的 fault handler，直接破坏 ART 的隐式空指针检查
   （ART 靠自己的 SIGSEGV handler 把 NPE 变成 Java 异常）。我们用普通 `sigaction`
   是有意的——待在 sigchain **内部**，只在链尾收到真崩溃。
2. **不给 handler 加 `si_addr` 门控**。review 建议只在 `si_addr` 落在跟踪的 dex
   页内时才打日志。**不采纳**：用户明确要求「不引入新假设」，而门控本身就是一个
   新假设（假设崩溃地址必然落在我们记录的页集合里，实际上 `#00 pc` 是在 SO 的
   代码段、`si_addr` 才是数据地址，两者关系未验证）。宁可多打几行，不可漏打。

**由此产生的残余风险**（真机必须验的第一件事）：整套设计依赖「`sigaction` 的
`oldact` 返回链中前一个 handler」。若 ART 的 sigchain 实际返回的是**已安装的
最外层**（即 `SIG_DFL`），我们的 handler 就会 shadow ART 的 fault handler，
把 ART 本可恢复的故障变成进程死亡。**验证方法**：打包一个会抛 NPE 的 App，
默认内存路径运行，看是否仍正常抛 `NullPointerException` 而不是 `SIGSEGV` 崩溃。

### 11.6 v1.0.8 启动崩溃 → v1.0.9 修复（`restoreRead` 用途混用）

诊断系统上线后第一次真机崩溃就抓到了根因（`docs/crash.log`）：

```
Fatal signal 11 (SIGSEGV), code 2 (SEGV_ACCERR), fault addr 0x7b4f924d10
Abort message: 'SIG11 addr=0x7b4f924d10 code=2
  loc=/data/user/0/com.xixin.box/Anonymous-DexFile@3818887144.jar!classes14.dex
  restoreRead=0 mprotect=-1 methodIdx=1038'
```

**根因**：`patchClass` 把「**是否开 RW 窗口**」和「**是否恢复 `PROT_READ`**」
两个独立决策绑成了同一个 `restoreRead`。`is_file_dex_location()` 只认
`i11111i111.zip`，而 ART 以文件方式 mmap 的 shell dex，location 里同样带
`Anonymous-DexFile`（见上面的 `loc=`）→ 误判为内存 dex → `restoreRead=false`
→ `if (restoreRead && dpt_mprotect(... RW ...))` 短路 → **窗口从未打开** →
`patchMethodInsns` 往只读页写明文 → `SEGV_ACCERR`。

- **崩溃版本**：v1.0.8（`loc=` / `restoreRead=` 字段为 v1.0.8 独有）
- **引入版本**：v1.0.7（Task 1.5 重写引入；`git diff v1.0.7 v1.0.8` 在
  `dpt_hook.cpp` 是纯新增 234 行、0 行删除/修改）

**修复（v1.0.9）**：把两个用途拆开——

- **开窗**：改为**无条件**。对内存 dex 这不改变权限（heap buffer 本就可写），
  但**不是零代价**：每个 segment 仍会走一次 `mprotect` 系统调用（在 class-loader
  lock 下），且**新增了一个原本不存在的失败面**——任一 `mprotect` 返回非 0 就
  `windowOpen=false`，整个 class 保持加密，表现为 VerifyError
  （**推断，未单独验证**；同 §10 gate 拒绝的失败形状）。这是刻意取舍：
  跳过开窗正是 v1.0.8 崩溃的原因
- **关窗**：仍由 `restoreRead` 决定（文件 dex 恢复 `PROT_READ`；内存 dex 不恢复，
  否则破坏相邻堆分配）
- 开窗失败的回滚同样加 `if (restoreRead)` 门控——只回滚我们改过的权限

**这不是回到 v1.0.6**：v1.0.6 是「整 dex 开窗 + 永不恢复」（`phase1-perf-plan.md:81`
记为缺陷 B4「权限位长期暴露」）；修复后仍是「页粒度 + 文件 dex 恢复」，
**Task 1.5 的安全改进全部保留**，只去掉那个错误的短路。

**遗留（未修，独立问题）**：`is_file_dex_location()` 用 `location` 字符串判断
本身不可靠（日志已证明文件 dex 会被判成内存 dex）。不修时后果退化为
「文件 dex 开了窗不关」= 权限暴露，**不崩**。要判准应改用**映射属性**
（如 `isShellInMemoryDex(begin)` 的地址分支），而不是 `location` 字符串。
