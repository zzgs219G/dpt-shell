## 1. 两条主线总览

```
【打包侧 dpt.jar（纯 Java，命令行）】
java -jar dpt.jar -f app.apk
  → 解析 CLI → AndroidPackage.protect()
  → 加密指令 + 产载荷 + 拼壳 dex + 写配置 + 重打包签名
  → 输出加壳 APK

【运行时 shell（native libdpt.so + 壳 dex）】
加壳 APK 安装启动
  → 系统加载 classes.dex（壳代码）
  → System.load(libdpt.so)：init_array 解密自身 .bitcode + 装 hook
  → JNI_OnLoad：读配置 + 风险检测 + 注册 JNI
  → ia() 初始化载荷 / cbde() 恢复 dex 元素
  → attachBaseContext 存真名 → onCreate 替换真实 Application
  → 类加载时 patchClass 解密指令
```

## 2. 产物结构（加壳后 APK 内部）

| 路径 | 内容 | 谁写 / 谁读 |
|---|---|---|
| `AndroidManifest.xml` | application=ProxyApplication，appComponentFactory=ProxyComponentFactory | `ApkManifestEditor`（AAB 是 `AabManifestEditor`）写 / 系统读 |
| `classes.dex` | **[shell dex \| 内嵌 zip \| u32 大端 zip 长度]** | `combineDexZipWithShellDex` 写 / `readZipLength` 读 |
| `classes2.dex`… | keep dex（文件形式，明文） | `addKeepDexes` 写 / 系统直接加载 |
| `assets/d_shell_data_001` | AES-CBC 加密的 shell config JSON | `writeConfig` 写 / `read_shell_config` 读 |
| `assets/OoooooOooo` | v4 指令恢复载荷 | `MultiDexCodeUtils.writeMultiDexCode` 写 / `readCodeItem`→`MultiDexCode::init` 读 |
| `assets/vwwwwwvwww/<abi>/libdpt.so` | 壳 so（`.bitcode` 段加密） | `copyNativeLibs`+`encryptSoFiles` 写 / 运行时 `unzipLibs` 解出后 `System.load` |
| `lib/<abi>/*.so` | 应用原始 so | 原样保留 |
| （运行时）`code_cache/i11111i111.zip` | 受保护 dex zip，**仅文件路径模式**（API≥29 默认走内存路径，见 §4.2） | `extractDexesInNeeded` 写 / `combineDexElement` 读 |

内嵌 zip 里的 entry 名是 `classes.dex`、`classes2.dex`…（STORE 不压缩）。

以上路径对应的 native 宏都在 `common/dpt_macro.h`：
`DEXES_ZIP_NAME`（i11111i111.zip）、`SHELL_CONFIG_IN_ZIP`、`CODE_ITEM_NAME_IN_ZIP`、
`COMBINE_DEX_FILES_NAME_IN_ZIP`、`CACHE_DIR`、`JUNK_CLASS_FULL_NAME`。

## 3. 打包流程（dpt.jar）

入口 `Dpt.main` → `parseOptions`（CLI→Builder）→ `androidPackage.protect()`。

```
Apk.protect()
├─ super.protect()  (AndroidPackage.protect)
│   ├─ 校验 shell-files/ 存在（不存在直接抛异常）
│   ├─ processRuleFile            ← -r 排除规则
│   ├─ processProtectConfigFile   ← -c 读 JSON → ShellConfig
│   ├─ 合并 CLI 覆盖配置           ← riskCheckFlags |= …；disableInmemoryDex 只能强制关
│   ├─ computeSignatureSha256     ← -vs 签名校验哈希
│   └─ JunkCodeGenerator.generateJunkCodeDex
└─ process(this)   ← 以下顺序即 Apk.process() 源码顺序
    ├─ encKey = KeyUtils.generateKey()          ← 一个随机 key，后面三处共用
    ├─ ZipUtils.unZip → workspace；读 packageName
    ├─ resolveDefaultShellPackageName           ← 随机化壳包名（反指纹）
    ├─ manifest：saveApplicationName → writeProxyAppName
    │            → [isAppComponentFactory: save+write ACF]
    │            → [isDebuggable: setDebuggable] → setExtractNativeLibs
    ├─ addJunkCodeDex        ← junk 并入 classes.dex（失败则独立 junkcode.dex）
    ├─ extractDexCode(encKey)   ← 逐 dex 并行，内部含 4 件事（见下方展开）
    │                             + 写 OoooooOooo v4 载荷（见 §5 配对规则）
    ├─ compressDexFiles      ← classes\d*.dex 规则 STORE → i11111i111.zip（+zipalign）
    ├─ deleteAllDexFiles
    ├─ combineDexZipWithShellDex  ← [shellDex|zip|u32be len] → classes.dex（修 header/sha1/checksum）
    ├─ addKeepDexes          ← keep dex 加回 APK 根（在 zip 之后，所以 zip 里没有它们）
    │   + 删 keepDexTempDir
    ├─ copyNativeLibs        ← shell so → assets/vwwwwwvwww/<abi>/
    ├─ encryptSoFiles(encKey)    ← 加密 so 的 .bitcode 段
    ├─ writeConfig(encKey)   ← 配置 JSON（含 key）→ AES 加密 → assets/d_shell_data_001
    └─ buildPackage          ← 重打包 → zipalign → 签名(v1/v2/v3) → 清 workspace
```

**`extractDexCode` 展开**（逐 dex 线程池并行，`CountDownLatch` 汇合；每 dex 依次）：

1. `injectInvokeMethod` → 注入 `JniBridge.clinit` 反射调用点，注入后覆盖原 dex。
2. `-K`（keep classes）时：`dexContainsKeepInPlace` 命中则**整 dex 跳过分区**（防 Compose
   的 IncompatibleClassChangeError）；否则 `splitDex` 分出 keep dex 到 `keepDexTempDir`。
3. `extractAllMethods` 逐类抽指令 → 产 `*_extracted.dat`（ChaCha20 密文 + v4 载荷记录）。
4. `writeHashes` 修 dex 头（`sha1`/`checksum`/`signature`）后覆盖回原 dex；
   若是 `classes.dex` 还取 `getDexSignature` 存入配置。
   最后 `MultiDexCodeUtils.writeMultiDexCode` 落 `OoooooOooo`。

### 3.1 密钥链（改动必须成对理解）

| 用途 | 打包侧 | 运行时侧 |
|---|---|---|
| **指令（insns）ChaCha20** | `extractMethod` 用 `ShellConfig.getInsnsCryptKey()`（`DexUtils.java`），nonce=`buildChaCha20Nonce(methodIdx)` | `g_shell_config.aes_key`（32B，`dpt.h ShellConfig.aes_key`）+ `build_chacha20_nonce`，`dpt_crypto` 执行；契约测试 `InsnsCryptoContractTest` |
| **配置 blob 加密** | `deriveConfigAesKey` = HMAC-SHA256(randomKey, packageName+"_"+buildKey)（测试 `ConfigKeyDerivationTest`） | `read_shell_config` 同式派生 |
| **so `.bitcode`** | `encryptSoFiles(encKey)`（`Apk.process()` 传入随机 `encKey`）：对 `.bitcode` 段做 `CryptoUtils.rc4Crypt(rc4Key, …)`，再用 `writeSoFileCryptKey` 把 `rc4Key` 写到 so 的动态符号 `DPT_UNKNOWN_DATA`（`Const.RC4_KEY_SYMBOL`）位置；找不到该符号只 warn、不写 | `decrypt_section`：RC4 key 直接取 `DPT_UNKNOWN_DATA`(16B) 的**当前内容**。so 里的初值 `"1234567890abcdef"` 在打包时被覆盖，**运行时 key 是打包器写入的随机值，不是编译期常量**；这段必须跑在 **init_array（System.load 时机，早于读配置）**，因为它是解密自身 |
| **buildKey 三方绑定** | `dpt.jar` 启动校验 `shell-files/build-key` | CMake 注入 `DPT_BUILD_KEY`（缺失则 FATAL）；同时参与配置密钥派生 |

`encKey` 由 `Apk.process()` 传给 **`extractDexCode` / `encryptSoFiles` / `writeConfig`** 三处
（`Apk.java` 调用点）。同一次打包的指令密文与配置必须配套，所以
**dpt.jar 与 shell-files 必须同一次构建**（AGENTS.md §5）。

## 4. 运行时流程（shell）

### 4.1 so 加载与 JNI_OnLoad

```
unzipLibs（assets/vwwwwwvwww → dataDir/dpt-libs/<abi>，abi 由 EnvUtils.getAbiDirName 探测）
→ System.load(libdpt.so)
├─ init_array → init_dpt()                    ← dpt.h 用 INIT_ARRAY_SECTION 声明
│   ├─ decrypt_bitcode()   ← CMake 无条件 -DDECRYPT_BITCODE，RC4 解自身 .bitcode 段
│   └─ dpt_hook()          ← Dobby: DefineClass/LoadClass；bytehook: mmap(+W)/execve(拦dex2oat)/write(dex签名)
└─ JNI_OnLoad
    ├─ read_shell_config()  ← ensure_package_loaded(1.8 mmap 缓存) → 读 d_shell_data_001 → 解密 JSON
    │                          → 派生 g_shell_config.aes_key → 定 g_use_in_memory_dex
    ├─ antiRisk()           ← 按 risk_check_flags 启风险检测线程
    └─ registerNativeMethods (ia/cbde/ra/craoc/rcf/rapn/gap/gdp/rde/clinit…)
```

### 4.2 dex 恢复（每进程一次，`Global.sIsReplacedClassLoader` 守卫）

三个入口，**守卫粒度不同**（源码逐处核对）：

```
① ProxyComponentFactory.instantiateClassLoader  (API ≥ 29，无守卫先手)
   unzipLibs → loadShellLibs → ia() → cbde(cl) → 置位
② ProxyComponentFactory.instantiateApplication  (API ≥ 28)
   if(!sIsReplacedClassLoader){ unzipLibs → loadShellLibs }   ← 仅这步在守卫内
   ia()                        ← 无条件调用（ia 幂等）
   rapn()
   if(!sIsReplacedClassLoader){ cbde(cl); 置位 }              ← 仅 cbde 在守卫内
③ ProxyApplication.attachBaseContext            (全版本兜底)
   if(!sIsReplacedClassLoader){ unzipLibs → loadShellLibs → ia() → cbde(cl); 置位 }
   realApplicationName = rapn()   ← 守卫之外，每次 attach 都跑
```

**关键点：只有 `cbde` 是每进程至多一次；`ia()` 在 ①②③ 里都是无条件调用**
（靠幂等性兜底）。Android 10（API 29）起 `instantiateClassLoader` 先跑并置位，
②③ 的守卫块随后跳过；Android 9 及以下没有 ① 这个回调（`instantiateClassLoader`
是 API 29 才加入 AppComponentFactory 的），只能靠 ②/③。

- **ia = `init_app`**：读 `assets/OoooooOooo` → `MultiDexCode::init(v4)`；
  `g_use_in_memory_dex == false` 时才 `extractDexesInNeeded` 落盘 zip。
  幂等靠 `g_codeItemFileData` 缓存（已读过就不再读）。
- **cbde = `combineDexElements`**：
  - in-memory 模式（`g_use_in_memory_dex`，API≥29 且配置未禁用，`read_shell_config` 一次性决定）
    → `combineInMemoryDexElements`：内嵌 zip 切出 → 每 dex 堆缓冲 → `NewDirectByteBuffer`
    → `InMemoryDexClassLoader(buffers, parent)` → 把它的 dexElements **追加**进目标 PathList
    （splice），登记地址白名单，缓冲与 loader 全程保活（ART 不拷贝）→ 失败则落盘回退。
  - 文件模式 → `getCompressedDexesPath` + `combineDexElement`（makePathElements 追加）。
  - 两种模式最后都跑 `junkCodeDexProtect`（`FindClass(JUNK_CLASS_FULL_NAME)`，与 zip 无关）。
- **cbde 每进程至多一次**是既有前提（文件模式重复追加会 DuplicateClass），
  由 `sIsReplacedClassLoader` 保证。

### 4.3 Application 替换（跨两个生命周期回调）

`rapn` 与 `ra`/`craoc` **不在同一节拍**，中间隔了一整个系统回调：
`rapn` 在 `attachBaseContext`（入口③）里只把真名存进字段，
真正的替换要等系统回调 `onCreate`（此时 `Application.attach` 已完成）。

```
ProxyApplication.attachBaseContext: … cbde(cl) → realApplicationName = rapn()   ← 只存真名
ProxyApplication.onCreate:
  replaceApplication()          ← 门控 Global.sNeedCalledApplication（初值 true）
  ├─ ra(realApplicationName) = replaceApplication
  │   ├─ replaceApplicationOnLoadedApk：makeApplication 建真实实例（内部已 attach）
  │   └─ replaceApplicationOnActivityThread：改 mInitialApplication
  └─ craoc(realApplicationName)：调真实 Application.onCreate
```

- `rapn()` 只读 `g_shell_config.application_name` 并返回，**不做替换**。
- **只有系统按 manifest 实例化了 ProxyApplication 时才需要这套替换**：
  `instantiateApplication`（入口②，API ≥ 28 且注入了 ACF）里 `rapn()` 拿到真名后，
  直接把真实 Application 返回给系统（`super.instantiateApplication(cl, applicationName)`），
  系统自己设 `mInitialApplication`，ProxyApplication 根本不会被实例化 ——
  此时 `instantiateApplication` 已把 `sNeedCalledApplication` 置 false，
  `onCreate` 里的 `replaceApplication()` 是空操作。
  API < 28（无 ACF），或 APK 未注入 ACF，则系统创建 ProxyApplication，
  才由 `onCreate` 的 `ra` + `craoc` 补替换。
- `replaceApplication()` 还会被 `ProxyApplication.createPackageContext` 调用，
  且它**直接 `return realApplication`**（返回的不是 Context 而是 Application）。
- `ProxyApplication.getPackageName()` 在替换完成前返回 `""`，用于拦截系统对包名的探测。
- `Global.sNeedCalledApplication` 初值 true；`ProxyComponentFactory.instantiateApplication`
  与 `replaceApplication()` 执行后都会把它置 false。

### 4.4 类加载时指令解密

```
DefineClass/LoadClass hook → patchClass(descriptor, dex_file, class_def)
  ├─ junk 类检查（descriptor 含 junk 且末位是数字 → dpt_crash）
  ├─ is_shell_dex_location(location, begin)   ← zip 路径 或 Anonymous前缀+已登记地址
  ├─ dexIndex = parse_dex_number(location)
  ├─ findClassIndex(dexIdx, classDataOff)     ← v4 载荷二分；找不到=未保护类，零副作用返回
  ├─ 按页锁 + 分段 mprotect RW（Task 1.5 将改：当前是整 dex RW 不恢复）
  └─ direct→virtual 顺序逐方法 patchOneClassMethod
        └─ patchMethodInsns → ChaCha20 解密写回（key=aes_key, nonce=methodIdx）
```

另有 `clinit` JNI：随机触发 `veritySignature`（`-vs` 开启时校验证书 SHA-256，
由打包侧 `injectInvokeMethod`/`ReflectionClinitInjector` 注入调用点）。

## 5. 数据格式契约（改一处必改另一处）

| # | 格式 | Java 侧（写） | Native 侧（读） |
|---|---|---|---|
| 1 | shell config JSON 字段名 | `ShellConfig.toJson()` + `@JSONField` | `read_shell_config` 的 `AY_OBFUSCATE(key)` + `value(key,默认)` |
| 2 | 内嵌 zip 尾部 `[dex\|zip\|u32be len]` | `combineDexZipWithShellDex` | `readZipLength`（`writeDexAchieve`/`combineInMemoryDexElements`） |
| 3 | v4 载荷 OoooooOooo | `MultiDexCodeUtils`（`Const.MULTI_DEX_CODE_*`） | `dex/MultiDexCode`（`DPT_MULTI_DEX_CODE_*`） |
| 4 | insns 加密 | `CryptoUtils.chacha20Crypt`（nonce=`buildChaCha20Nonce(methodIdx)`） | `dpt_crypto.chacha20_crypt_insns`（`build_chacha20_nonce`） |
| 5 | **dex 下标三方一致** | `DexUtils.getDexNumber`：正则 `classes(\d*)\.dex$`，classes.dex→0、classesN.dex→N-1、其他→-1（`DexUtils.java` 已核对） | `parse_dex_number(location)`：兼容 `!classesN.dex`（旧）与 `!N`（新，Android 17 起）两种后缀；in-memory 时还等于 **buffer 在数组中的位置**（须连续 0..n-1） |
| 6 | 配置加密密钥派生 | `deriveConfigAesKey` = HMAC(randomKey, pkg+"_"+buildKey) | `read_shell_config` 同式（pkg 来自 ApplicationInfo，buildKey=`DPT_BUILD_KEY`） |
| 7 | 方法顺序 | `ClassData.allMethods()` = direct→virtual | `patchClass` 解析 direct→virtual |

### 5.1 v4 载荷配对细则（最容易踩的坑）

- 类的键 = `class_data_item` 偏移：`Instruction.setClassDataOff` ↔ `findClassIndex(dexIdx, classDataOff)`。
- **位置配对**：运行时按 `ClassData.allMethods()` 顺序逐方法消费 `MethodData`，
  打包侧必须**每个被遍历的方法产出恰好一条记录**。
  native/abstract/shared-code 等未抽取的方法写 **`insnsSize=0` 占位**
  （`DexUtils.placeholderInstruction`），运行时见 0 即跳。
  **缺一条 → 同类后续方法全部错位**：后果不是少保护一个方法，而是把该类
  **后续所有方法的密文整体错位一格**（v1.0.1 启动即崩的根因，
  详见《启动闪退根因分析.md》；`placeholderInstruction` 的注释有事故说明）。
- 排除规则（`-r`）命中的类**整类不在载荷**（`extractAllMethods` 里 `matchRules` continue）
  → 运行时 `findClassIndex` 找不到 → 视为未保护类，零副作用。
- keep/split 分区由 `DexUtils.splitDex` 按 `ProtectRules` 完成；Compose 等
  keep-in-place 类整 dex 跳过分区（`dexContainsKeepInPlace`，防 IncompatibleClassChangeError）。

**加一个配置字段 = 改第 1 行两侧 + `ShellConfig.init()` 拷贝 + `AndroidPackage.protect()` 合并（若需 CLI）。**
实例对照：Task 1.4 的 `disable_inmemory_dex`（见《进度与交接》§4）。

## 6. 关键不变量（改代码红线）

1. `insnsSize` 是**字节数**不是 code unit 数。
2. direct→virtual 顺序两侧契约；**载荷记录数 = 方法遍历数**，缺记录=密文错位。
3. `cbde` 每进程至多一次；`ia` 可多次（幂等）。
4. `dpt.jar` 与 `shell-files/` 必须同次构建（build-key 校验）。
5. `findClassIndex` 必须在 mprotect **之前**（payload 外的 dex 零副作用）。
6. in-memory dex：buffer 数组位置 = payload dexIdx，编号必须连续
   （ART 给第 i 个 buffer 分配运行时 multidex 后缀，`parse_dex_number` 再转回 i；
   有空洞会让后续 dex 下标整体错位，`combineInMemoryDexElements` 有连续性检查）。
7. 恢复权限前要刷 i-cache（Task 1.5 引入 `__builtin___clear_cache`）。
8. `jni::NewObject` 在 `GetMethodID` 失败时**不清异常**，调用点需自行 ExceptionClear。
9. Native 编译只能靠 CI；**不要写本地语法检查脚本**（AGENTS.md §6 教训）。
10. 不要在 commit message 加 `Co-Authored-By` trailer（AGENTS.md §7）。
11. so 的 `.bitcode` 解密跑在 init_array（早于配置）——**不能**改成依赖配置的 key
    （key 由打包器写入 `DPT_UNKNOWN_DATA`，运行时还没读配置）。
