### 1.1 本轮补上的缺口

**接手者拿到一个 `.apk`，原先无法快速判断它来自哪个模块组合。**
这不是小问题——两个组合的故障定位路径完全不同：

| 组合 | 崩溃时的第一嫌疑 | 测试重点 |
|---|---|---|
| 只勾 packer | dpt 自身（派生链/配置/载荷） | 三条链是否通 |
| 全模块 | 联动（桩进壳 dex、`gseed`、dex2c 产物） | 联合链路是否通 |

**但两者在 dpt 侧的症状都是 `SIGABRT` + 一句 dpt 日志**，
分不清就会往错误方向查。历史上这正是浪费时间的主要来源。

现已补 `scripts/dev/identify-combo.sh`，判据见 §2。

## 2. 组合识别判据（实测）

```bash
scripts/dev/identify-combo.sh <apk>
```

### 2.1 判据表

| 判据 | 只勾 packer | 全模块 | 全模块不勾 packer | 可靠性 |
|---|---|---|---|---|
| `assets/xixin/*/libxixin.so` | ✅ | ✅ | ❌ | 判断「是否壳包」 |
| `lib/*/libnc.so` | ❌ | ✅ | ✅ | **高**（sigcheck/dex2c/envcheck 才有） |
| 壳 dex 里 `GAMMA`/`keyByte`/`mix64` | ❌ | ✅ | ✅ | **高**（stringenc 桩结构不变量） |
| `assets/xixin_data` blockCount | 有值 | 有值 | 无 | 反映抽取强度 |

**「全模块不勾 packer」是最容易误判的一类**：它没有壳包特征，
`[kl]` 日志不会出现，拿 `verify-on-device.sh` 跑会判 FAIL —— 那是预期的。
`identify-combo.sh` 会明确提示这一点。

### 2.2 为什么不能靠类名

stringenc 的桩类名**每包随机**（防固定签名）。实测全模块产物里
`grep -c strdec` = **0**。必须用桩骨架的结构不变量：
`GAMMA`（splitmix64 增量常量）、`keyByte`、`mix64` —— 这三个名字
不参与随机化（是 `--emit-stub-filter` 的固定目标）。

### 2.3 判据实现的坑（已踩）

```bash
# ❌ 错：grep -q 命中即退出 → SIGPIPE 杀掉 unzip → 整条管道判失败
unzip -p "$APK" classes.dex | strings | grep -qE 'GAMMA|keyByte|mix64'

# ✅ 对：先落临时文件
unzip -p "$APK" classes.dex > "$TMPDE"
strings "$TMPDE" | grep -E 'GAMMA|keyByte|mix64' >/dev/null
```

实测后果：全模块包被判成「部分模块」。**这类管道陷阱在排障脚本里
很常见，写判据时要特别注意。**

## 3. 仍存在的缺口（按严重度）

### 3.1 【中】apk-protect-action 没有交接文档

| 现状 | 影响 |
|---|---|
| 入口是 `docs/流程文档.md`（**1879 行**） | 新接手者要读完才能动手 |
| 有 `AGENTS.md`（155 行，工作纪律） | 只讲纪律，不讲"现在是什么状态" |
| 文档按模块分节（§3.7 stringenc / §3.10 packer / §3.11 签名联动…） | 缺"拿到产物怎么判断组合"的入口 |

**建议**：给 apk 仓库补一份 `docs/交接文档.md`，仿 dpt 侧结构：
现状（版本坐标 + 生效工具包 sha256）→ 模块清单与依赖关系 →
组合识别（指向 `identify-combo.sh`）→ 验收口径 → 未完成事项。

### 3.2 【低】dpt 侧文档对「联动」描述偏少

交接文档 §8.4 只写了"部分已实现，未做逆向评估"。
对只维护 dpt 的人够用，但如果接手者要动联动，需要读 apk 侧的 §3.7.4。

**建议**：在交接文档 §2 末尾加一句指向
`../apk-protect-action/docs/流程文档.md` §3.7.4（桩的 SEED 链路）。

### 3.3 【低】两个仓库没有共同的"总入口"

接手者可能先打开任意一个仓库就动手。

**建议**：两个仓库的 `AGENTS.md` 首段都加一句：
「本项目由两个仓库组成，另一个在 `../<name>/`，先读那边的交接文档」。

### 3.4 【已知】真机验证仍需人工

无电脑 → 无法自托管 runner。当前形态是"用户手动跑一条命令"。
`scripts/dev/README.md` §CI 自动化 已写明三种方案与取舍。
