# dpt-shell 启动闪退根因分析

> 记录 v1.0.1~1.0.3 打包 APK 启动闪退的根因（及 v1.0.4 的修复），
> 以及 v1.0.5 内存加载路径 VerifyError 的根因（第九节，后续新增）。
> 结论由 git 历史 + 源码复核 + 版本消减实验反推得出。

---

## 一、现象

- **v1.0.0**：正常，能启动。
- **v1.0.1 / v1.0.2 / v1.0.3**：打包出的 APK 一点都跑不起来，启动即闪退。
- **v1.0.4**：恢复正常。

真机崩溃栈（Redmi / Android 16 / `com.xixin.box`）：

```
#00 pc 0x58078   /data/data/com.xixin.box/dpt-libs/arm64/lib*.so
#01 pc 0x44a24   lib*.so
#02 pc 0xa42dc   lib*.so
#03 pc 0xa45c4   lib*.so
#04 pc 0x2250cc  /apex/com.android.art/lib64/libart.so
      (art::ClassLinker::DefineClass(...)+4940)
#05 pc 0x23641c  libart.so (FindClassInBaseDexClassLoader)
#06 pc 0x6140ec  libart.so (VMClassLoader_findLoadedClass)
```

崩溃点全部落在 `libdpt.so` 内部，调用方是 ART 的 `ClassLinker::DefineClass`
—— 即**壳在 ART 定义类的路径上还原指令时出的问题**。

---

## 二、引入点

```
9f9d2dd  feat: OoooooOooo v4 载荷格式 + 打包侧 IO 优化 + 基准工具
```

v4 把密文与方法的配对方式从 **「按 `methodIdx` 索引寻址」** 改成
**「按类内位置递增配对」**（runtime 遍历一个类的每个方法，就按顺序消费一条
`MethodData` 记录）。方向没错，但这次重构**静默推翻了三个旧前提**，
形成三个各自独立、都能致命的缺陷。

---

## 三、三个根因

### 根因一：解密指令写入只读 dex 页（1.0.1~1.0.3 闪退的首要原因，1.0.4 修）

**提交**：`0af9fbf` 引入，`c4f41df` 修复。

`0af9fbf` 判定 `change_dex_protective()` 与 `dexMemMap` 是「v4 改造后失去调用者的
死代码」并删除。但它没注意到：写 dex 的职责虽然从 `patchMethod` 搬到了
`patchMethodInsns`，**写权限保障却没跟着搬**。

v1.0.0 的 `patchMethod` 在写之前必调 `change_dex_protective()`，把
`[begin, begin+dexSize)` 设为 `PROT_READ|PROT_WRITE`，并用 `dexMemMap` 做 memo。
删掉之后，只剩 `hook_mmap` 里的 `fake_mmap` 一个兜底 —— 而 `fake_mmap` 只对
**经过被 hook 的 libc `mmap`** 加载的 dex 生效。

**代码里的直接痕迹**：`patchClass` 取到了 `dexSize` 却从不使用 —— 它正是
`change_dex_protective` 需要的第二个参数。一个「取了不用」的参数，指向一次
「删错了东西」。

复核确认 1.0.1（`f2580f8`）的写权限防线**完全押在 `fake_mmap` 这一个单点上**：

| 检查项 | v1.0.0 | v1.0.1 (f2580f8) |
|---|---|---|
| 显式 `mprotect` 调用 | 有 | **全文零次** |
| `dexMemMap` memo | 有 | **不存在** |
| `change_dex_protective` | 有 | **不存在** |
| 调用点 | 有 | **无** |
| `fake_mmap` 升级 `PROT_WRITE` | 完好 | 完好 |
| `hook_mmap()` 已安装 | 是 | 是 |

**修复**（`c4f41df`）：恢复 `change_dex_protective()`，参数改为 `uint64_t dexSize`
（`patchClass` 里 `dexSize` 已是 `uint64_t`，传 `int` 会截断大 dex），
在 `class_data_off_ != 0` 分支内、`findClassIndex` 之前调用，并恢复 `dexMemMap` memo
与 `<map>` 头文件。

**关键约束**：只调用一次 `mprotect`/dex，**不能**放进 `patchMethodInsns` 的每方法路径
—— `patchClass` 运行在 ART 的 class-loader 锁内。

### 根因二：`getMethodData` 边界检查基准错误（1.0.2 修）

**提交**：`9f9d2dd` 引入，`69a8741` 修复。

```cpp
// 修复前
const uint8_t* base = m_buffer + m_methodDataOffset;
size_t off = entry->methodDataOff;
for (uint16_t i = 0; i < index; i++) {
    if (off + 6 > m_size) return view;   // ← 基准错了
    uint16_t sz = readUInt16At(base, off + 4);
    off += 6u + sz;
    if (off > m_size) return view;       // ← 基准错了
}
```

`methodDataOff` 是**相对 methodData 区起点**的偏移，却拿去和 **payload 总长 `m_size`**
比较。methodData 区远小于 payload 总长，所以合法范围内的 `off` 永远小于 `m_size`，
这个检查形同虚设 —— 越界值只要没超过总长就会被放行，`readUInt16At` 直接读到缓冲区之外。
payload 是 `mmap` 出来的，越界读就是 SIGSEGV。

**为什么测试没抓到**：跨语言对拍用的 payload 只有 126 字节，构造的越界值恰好没超过
总长，两种算法都「通过」了。这是**测试覆盖不足，不是算法侥幸正确**。
本次用 ASan 复现 —— 旧算法直接报 heap-buffer-overflow。

**修复**：统一基准，用 methodData 区剩余长度 `avail = m_size - m_methodDataOffset`
做全部四处比较。

### 根因三：载荷方法错配（1.0.3 修）

**提交**：`9f9d2dd` 引入，`5ed1332` 修复。

v4 契约要求：打包侧对 runtime 遍历到的**每个**方法都产出一条 `MethodData` 记录。
但 `DexUtils` 有四处 skip 是**不产记录**的：

- `method.getCodeOffset() == 0` —— abstract / native
- `code.getInstructions().length == 0` —— 空方法体
- `insnsCapacity * 2 < return 长度` —— 容量不足
- `getCodeOffAppearCount() > 1` —— code_item 被多方法共享

其中**任何一处 skip 都不只是少保护一个方法**，而是把它之后的所有方法**整体错位一格**：
前一个方法的密文被写进后一个方法的方法体。ART 在 `ClassLinker::DefineClass` 里
一边解密一边校验 dex，于是直接 `VerifyError` / SIGSEGV。

**为什么 v1.0.0 不中招**：它建 65536 槽的表并用 `codeItemVec->at(methodIdx)`
**按索引**取密文，缺一条记录只影响那一个 `methodIdx` 本身，不会波及后续方法。

**修复**：新增 `placeholderInstruction()`，让上述四处 skip 改为产出一条
`insnsSize = 0` 的占位记录（6 字节，带正确的 `methodIdx`）。runtime 的
`patchMethodInsns` 见到 `insnsSize == 0` 立即返回，什么都不写，方法体不被触碰；
位置配对因此恢复恒等。

class 级的三处 `continue` 不需要改：类被排除时它的方法体根本没被抽空，
native 侧 `findClassIndex` 返回 `nullptr` 会整体跳过该类，不存在错位。

**实测数据**（真实 APK）：

| APK | dex 数 | 记录数 == 遍历数 | 错配 |
|---|---|---|---|
| orig.apk | 21 | 222837 == 222837 | 0 |
| target.apk | 1 | 9448 == 9448 | 0 |
| min2.apk | 1 | 32 == 32 | 0 |

修复前 `target.apk` 上有 **126 个方法坏掉**（31 无记录 + 95 密文错配）。

## 四、为什么必须三个都修

前两个根因各自足以致命，**修完前两个仍会崩**，因为第三个还在。修复过程本身就是
一次消减实验：

| 版本 | 修了什么 | 实测结果 |
|---|---|---|
| v1.0.2 | 根因二（边界基准） | **仍崩** |
| v1.0.3 | 根因三（载荷错配） | **仍崩** |
| v1.0.4 | 根因一（只读页写入） | **恢复** |

这条链把因果关系钉死了：既然修完前两个还崩，就**必然**存在第三个独立缺陷；
而唯一剩下的、且修完就不再崩的，就是根因一。

## 六、排除的假设

`docs/系统报错日志.md` 里那份 AI 审核当时怀疑的是 **V35 `DexFile` 布局问题**，
建议把 `g_sdkLevel >= 35` 改成 `< 36` 让 Android 16 回退 V28 分支。

**该假设不是根因**：崩溃栈的调用方是 `ClassLinker::DefineClass`，而真正的证据在
「`dexSize` 取了不用」这个痕迹和 `0af9fbf` 的删除 diff 里。回退 V28 分支走不通。

## 七、置信度与未验证项

| 结论 | 置信度 |
|---|---|
| 三个缺陷客观存在（已逐个读回文件确认） | 99% |
| 根因二（越界检查） | 95% |
| 根因三（载荷错配） | 95% |
| 根因一（只读页写入） | 85% |

**根因一为何是 85% 而非 95%**：`fake_mmap` 挂的是 art lib 的 `libc.so` PLT，
只对经由被 hook 的 libc `mmap` 加载的 dex 生效 —— 这一点已确认。但
**「Android 16 的 ART 确实绕过了该 hook」没有 ART 源码级证据**。

**待验证**（需要 adb 真机）：在 Android 16 设备上把 `fake_mmap` 临时改成只打日志、
不升级 `PROT_WRITE`，看崩溃是否依旧：

- 依旧崩溃 → 机制确认，根因一可提至 95%
- 不再崩溃 → 说明 `fake_mmap` 本该兜住，根因一的机制描述需要修正

> 本机为 arm64，无法编译 native（见 `AGENTS.md` 第 6 节），编译由 CI `build.yml` 验证。
> 上述真机实验**尚未执行**，1.0.4 的真机启动表现也**尚未实测**。

## 八、教训

1. **删除「死代码」前，先确认它是否承载了某个副作用。** `change_dex_protective`
   的调用者没了，但它的**职责**（保证 dex 页可写）仍被别的路径需要。
   一个「取了不用」的参数就是这类遗漏的痕迹。
2. **改配对契约时，要同步清点所有不产记录的路径。** 从「按索引寻址」改成
   「按位置配对」，等于把所有 skip 从「局部影响」升级成「全局错位」。
3. **对拍测试的输入太小会掩盖基准错误。** 126 字节的 payload 让错误基准
   「恰好通过」；关键边界要用 ASan 或真实规模的数据压。

## 九、v1.0.5：内存加载路径的地址白名单拒绝（VerifyError）

> 2026-10 新增。Task 1.4（InMemoryDexClassLoader 内存加载）真机首跑即触发，
> 由 `--disable-inmemory-dex` 对照实验定案。

### 现象与对照实验

同一工具、同一 App（`com.xixin.box`，14 dex，Redmi / Android 16）：

| 打包方式 | 结果 |
|---|---|
| 默认（内存加载） | **必崩** `java.lang.VerifyError: Verifier rejected class com.xixin.box.xiApplication` |
| 加 `--disable-inmemory-dex` | **正常启动** |

崩溃特征：`xiApplication` 的 8 个方法全部是垃圾字节；dex 位置
`/data/user/0/com.xixin.box/Anonymous-DexFile@2086524492.jar!classes14.dex`
（`!classes14.dex` 后缀证明内存路径已生效，dexIdx=13）。

对照实验一次定案：payload、配对、契约、打包侧提取全部正常（文件模式能跑），
**唯一变量是内存加载路径下 patch 从未发生** —— 方法体保持打包时的随机填料
（默认 `obfuscate = !smaller = true`），verifier 拒绝。

### 根因（演绎闭合）

`patchClass` 的 gate（`is_shell_dex_location`）是内存/文件模式唯一的差异环节：

```cpp
location 含 "i11111i111.zip"                          → 文件模式，放行
location 含 "Anonymous-DexFile" && isShellInMemoryDex(begin) → 内存模式
```

崩溃 location 含 `Anonymous-DexFile` → 前缀条件命中 →
**必然结论：`isShellInMemoryDex(begin)` 返回 false**，即 ART 交给
`DefineClass` 的 `DexFile::begin_` 不落在 shell 注册的
`[NewDirectByteBuffer 地址, +size)` 区间内。Android 16 的 ART 没有把我们
注册的 buffer 地址直接暴露给 DexFile（注册端注释原断言「ART 引用不拷贝
（NonOwningMemoryRegion）」——该断言此前无源码依据，本次实验证伪其推论）。

gate 失败后**无任何日志直接 return**（release 构建下所有 `DLOG*`/`NLOG`
又被编译掉，`dpt_log.h` + `CMakeLists.txt` 仅 Debug 定义 `DEBUG`），
于是零日志、8/8 方法全坏、VerifyError —— 三个症状与该机制完全吻合。

被排除的备择假设：跨语言 payload 契约不一致（逐字段核对一致）、
`ClassIndexEntry` 布局不一致、`parse_dex_number`（对 `classes14.dex` 正确
返回 13）、methodIdx 错位（会打 `payload order mismatch` 日志且 8/8 全坏
不可能）、打包侧 HashMap 竞态 / 空 catch 截断（代码 1.0.4→1.0.5 未变更，
且文件模式能跑证明 payload 完整）。

### 修复

1. **`dpt.cpp` 注册表加内容指纹**：`registerShellInMemoryDex` 登记时快照
   112 字节 dex header；`isShellInMemoryDex` 先按地址（快路径），未命中再
   `memcmp` header 内容。dex header 含整文件 checksum + SHA-1 signature，
   外来匿名 dex 不可能碰撞，原保护语义（防误 patch 应用自己的
   InMemoryDexClassLoader）保持不变。
2. **`dpt_hook.cpp` gate 拒绝时补 `DLOGE`**（Debug 构建可见），消除这类
   静默失败的排障盲区。
3. 修正注册端「ART 引用不拷贝」的过强断言注释（`dpt.cpp` / `dpt.h`）。

patch 目标本就是 ART 的 `begin_`（无论它是我们的 buffer 还是 ART 自己的
拷贝），所以指纹放行后写入即生效，无需关心 ART 内部如何处理 buffer。

### 置信度与验证状态

| 结论 | 状态 |
|---|---|
| gate 地址白名单拒绝 = 根因 | 演绎闭合 + 对照实验定案 |
| 修复代码落地 | 已完成，**待 CI 编译验证**（本机无法编译 native） |
| 修复后真机启动 | **待验证**（需重新 `./gradlew build` 产出 so 后打包实测） |

### 新增教训

1. **release 构建把全部 native 日志编译掉，静默失败 = 不可诊断。**
   关键判定路径（gate 拒绝、索引未命中）必须补日志，且要意识到
   release 下仍然不可见 —— 排障要么用 Debug 构建，要么靠对照实验。
2. **「外部系统会引用我们的内存」这类假设必须实测，不能凭框架文档推断。**
   Task 1.4 的地址白名单整个建立在「ART 不拷贝 buffer」之上，
   该假设从未真机验证过（进度文档验收栏全部是 ⏳）。
3. **对照实验（一个开关）比十份 AI 分析更快定案。** 本次三份参考分析中
   两份找到了真 bug 但机制链均与本案无关，`--disable-inmemory-dex`
   一次实验直接把问题夹到内存路径内。
