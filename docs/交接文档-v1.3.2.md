### 1.1 拿到一个 APK，先判断它是什么组合

**这一步不能跳过。** 不同组合的故障定位路径完全不同：

| 组合 | 崩溃时第一嫌疑 | 产物是壳包？ |
|---|---|---|
| 只勾 packer（dpt） | dpt 自身三条链 | ✅ |
| 全模块（含 packer） | 联动（桩进壳 dex、`gseed`、dex2c） | ✅ |
| **全模块但不勾 packer** | stringenc/dex2c 自身 | ❌ 不是 |
| 未加壳原包 | — | ❌ 不是 |

**第三类最容易误判**：全模块但不勾 packer 时，产物没有 `.bitcode` /
`xixin_config` / `xixin_data`，业务 dex 也未被抽取，`[kl]` 日志
**不会出现**。拿它跑 `verify-on-device.sh` 会判 FAIL —— **那是预期的**。

```bash
scripts/dev/identify-combo.sh <apk>
```

判据（实测，详见 [完整性分析-接手评估.md](./完整性分析-接手评估.md) §2）：

| 判据 | 只勾 packer | 全模块 | 不勾 packer |
|---|---|---|---|
| `assets/xixin/*/libxixin.so` | ✅ | ✅ | ❌ |
| `lib/*/libnc.so` | ❌ | ✅ | ✅ |
| 壳 dex 含 `GAMMA`/`keyByte`/`mix64` | ❌ | ✅ | ✅ |

⚠️ **不能靠类名判断 stringenc**：桩类名每包随机，实测全模块产物
`grep -c strdec` = **0**。必须用桩骨架的结构不变量（那三个名字不参与随机化）。

## 2. 密钥派生链（唯一权威定义）

**两条链，共用 `seed + 证书 DER + 包名`，但 master 组成不同。这个差异是刻意的。**

### 2.1 段密钥（壳 so 的 `.bitcode`）

```
master = SHA256( seed_8(LE) || CRC32(.text)_4(LE) || "dpt-kl-v1" )
salt   = SHA256( certDER )
info   = "dpt-sec-v1" + pkg
key    = HKDF-SHA256(ikm=master, salt, info, len=16)   // 用作 RC4 key
```

输入来源：

| 输入 | 打包侧 | 运行期 |
|---|---|---|
| `seed` | root `build.gradle` 生成 → 持久化 `build/dpt-build-ids.properties` → `-DDPT_KL_SEED` 传 4 ABI → 落盘 `shell-files/keyladder-seed.txt` | 编译期宏 `DPT_KL_SEED` |
| `CRC32(.text)` | `SoSectionLocker` 读 so 文件 `.text` 段 | `dpt_keyladder.c` 解析运行期 so 文件 `.text` |
| `certDER` | `KeyLadder.extractFirstCertDer(--cert-source 或 -f)` | `dpt_cert_first_signer()` 从已安装 APK 提 |
| `pkg` | 从 APK 解析 | `/proc/self/cmdline` |

**每个 ABI 的 so 各自加密自己的 `.bitcode`**，所以可以绑定 `.text`。

### 2.2 配置 + dex 载荷

```
master_cfg = SHA256( seed_8(LE) || "dpt-cfg-master" )     // 刻意不含 CRC
salt       = SHA256( certDER )
info       = "dpt-cfg-v1" + pkg
material   = HKDF-SHA256(master_cfg, salt, info, 48) = [ aes_key(32) || iv(16) ]
```

- `aes_key` 同时用于：`xixin_config` 的 AES-CBC 解密、`xixin_data` 的 ChaCha20 区块解密
- `iv` 用于配置的 AES-CBC

### 2.3 为什么配置链不能含 CRC32(.text)

4 个 ABI 的 so 各有不同的 `.text` CRC（实测 arm=`0xf38fa79d`、
arm64=`0xbbb30a8d`、x86=`0x359a023e`、x86_64=`0xe50120a1`）。
配置只有**一份**，运行期在哪个 ABI 上跑就算出哪个 CRC ——
若 master 掺了它，同一份配置在不同 ABI 上必然解不开。

**代价（明确接受）**：配置/载荷链失去"改 `.text` 即自毁"的自绑定，
仍绑 seed + 证书 + 包名。真正的隔离点是派生链本身（seed 不在 APK 里）。

### 2.4 产物里没有任何密钥材料

`DPT_UNKNOWN_DATA` 符号**已删除**。运行期所需材料全部现算。

## 3. 三条必须守住的不变量

改代码前逐条对照，破坏了任何一条都会导致真机启动崩溃。

### 3.1 字节序：CRC32 必须小端

```java
// Java 侧必须显式指定
ByteBuffer.allocate(4).order(ByteOrder.LITTLE_ENDIAN).putInt((int) crc32Text)
```

```c
// C 侧 `&text_crc` 在 ARM 上天然是小端
mbedtls_sha256_update(&ctx, (const uint8_t *) &text_crc, 4);
```

**`ByteBuffer` 默认大端**，不显式指定就与 C 侧不一致 → key 不同 → `SIGABRT`。

### 3.2 运行期 APK 路径必须由 Java 传入

`.bitcode` 解密跑在 `init_array`，那时：
- `/proc/self/maps` 里**还没有** `base.apk`（ART 尚未映射）
- 壳 so 在 `dataDir/dpt-libs/<abi>/`，路径里没有 `/lib/`，无法反推

所以 `FileUtils.unzipLibs()` 在 `System.load` 之前调
`Os.setenv("DPT_APK_PATH", sourceDir)`，C 侧 `getenv` 直读。
**不要**改成"让 C 自己探测"。

### 3.3 四条链的密钥必须同源

| 用途 | 密钥来源 | 两侧对应 |
|---|---|---|
| `.bitcode` RC4 | `deriveKey(...)` | `dpt_kl_derive_section_key()` |
| 配置 AES-CBC | `deriveConfigMaterial()[0:32]` + `[32:48]` | `dpt_kl_derive_config_material()` |
| dex 载荷 ChaCha20 | `deriveConfigMaterial()[0:32]` | 同上（运行期 `g_shell_config.aes_key`） |

**改任何一条，必须同时改两侧并跑三方对拍**（见 §5）。

## 5. 验证方法与验收口径

### 5.1 本地可做（不需要 NDK）

```bash
# Java 单测（含两个关键回归）
./gradlew :dpt:test
#   computeMaster_crcIsLittleEndian           ← 钉字节序
#   deriveConfigMaterial_matchesCSide_andIgnoresAbi  ← 钉配置材料

# 宿主对拍（需 openssl；-DDPT_KL_HOST_TEST 关掉 android 日志）
FAKE=<只含空 mbedtls/sha256.h 与 mbedtls/hkdf.h 的目录>
clang -std=c11 -Wall -Wextra -Werror -Wno-deprecated-declarations \
  -DDPT_KL_HOST_TEST -I"$FAKE" -I. -Iexternal/mbedtls/include \
  tests/test_keyladder_ossl.c dpt_cert.c -o t -lcrypto && ./t
# 期望 derive = 9b76af40d3ec2fb0c840166e66dd7a23
```

**三方对拍**：任何派生公式改动，Java / C / 独立脚本三份实现必须同值。
配置材料基准值：

```
aes_key = 9fdfe58818a84c3bfa8cc6da17c1e3256e853522dbe73466b871c512813444a9
iv      = ab103d97c78df4212f26c979e4f0c57f
```
（输入：seed=`0xc640134a43c8b37e`、certDER=基线 APK 证书、pkg=`com.xixin.box`）

### 5.2 只能靠 CI

`dpt.cpp` 依赖 minizip 等头文件，本机（Termux arm64）编不了。
**Native 改动必须靠 GitHub Actions**，不要写本地语法检查脚本（AGENTS.md §6）。

### 5.3 真机验证

```bash
scripts/dev/verify-on-device.sh <apk> --device <host:port>
```
参数与判据详解见 [scripts/dev/README.md](../scripts/dev/README.md) §1。

判据（来自基线文档 §3）：

| 判据 | 含义 |
|---|---|
| `[kl] ... derive_rc=0` | 派生链成功 |
| 无 `config:` 错误 | 配置链成功 |
| 无 `materializeBlock` 失败 | 载荷链成功 |
| 无 `java_class == null` | JNI 注册成功 |
| 进程存活 | 最终判据 |

**该测两个组合**：① 只勾 packer ② 全模块。
历史经验：dpt 自身的 bug 只勾 packer 就能复现，是最快的定位手段。

### 5.4 产物静态核验（改动后必须复现）

| 检查 | 期望 |
|---|---|
| `.bitcode` 熵 | > 7.9 |
| 配置能解出合法 JSON | ✅ |
| 载荷块全部能解压 | 100% |
| `readelf -sW --dyn-syms \| grep -c DPT_UNKNOWN_DATA` | **0** |
| `readelf -SW \| grep -c '\.comment'` | **0** |
| `grep -ac` 四个派生常量 + `keyladder` | **全 0** |

## 6. 注释规范（重要，本版新增）

这轮迭代修了 9 个版本，注释里堆积了大量历史叙述，导致难以分辨
"当前事实"与"历史教训"。**从本版起按以下规则：**

### 6.1 代码注释只写三类内容

1. **现在是什么**（契约、公式、输入输出）
2. **为什么这样设计**（不这样会怎样，一句话说清）
3. **改这里要注意什么**（红线）

### 6.2 禁止写进代码注释的

- ❌ 版本号历史（"v1.2.6 因为 X 崩了"）
- ❌ 排障过程（"我一开始以为是 Y"）
- ❌ 已验证/未验证的状态（属于文档，会过期）
- ❌ 长篇事故复盘

**这些一律写进 `docs/基线-v1.3.2-真机验证.md` §5 或本文件 §7。**

### 6.3 判断标准

> 读注释的人只关心"我现在这么写对不对"。
> 如果他需要知道"以前错过什么"，那属于文档，不属于注释。

### 6.4 已有注释的处理

本版已按此规则精简 `dpt_keyladder.c/.h`、`AndroidPackage.java`
的注释（历史统一指向基线文档 §5）。新增代码请遵守同一规则。

## 7. 历史教训索引（要看细节来这里）

完整失效链见 [基线文档 §5](./基线-v1.3.2-真机验证.md)。此处只列结论：

| 教训 | 一句话 |
|---|---|
| 删共享载体前列全消费者 | `encKey` 同时喂配置链与载荷链，漏一个就断链 |
| 对拍参数不能取退化值 | `CRC=0` 时大端小端相同，字节序 bug 被完全掩盖 |
| 声称"已验证"前必须真跑 | 相邻字面量在编译期被合并，只看源码会得出错误结论 |
| fail-closed 必须带分步日志 | 否则 `SIGABRT` 只能靠猜 |
| 本地验证必须用真实输入形态 | 拿已签名包测，测不出"流水线喂未签名中间包"的问题 |

## 8. 未完成事项（按优先级）

### 8.1 真机回归自动化（Tailscale 方案，待评估）

**做法**：被测机装 Tailscale（WireGuard 私有 mesh，`100.x.x.x`，
**不是公网隧道**）→ `adb tcpip 5555` → CI 用 ephemeral authkey 加入 tailnet
→ `adb connect 100.x.x.x:5555` → 跑 `verify-on-device.sh`。

**必要安全约束**（缺一不可）：
- Tailscale ACL 只放行 `tag:ci` → `tag:test-device:5555`，其余拒绝
- 用 ephemeral + tag 的 authkey，可随时吊销
- 被测机不含个人数据

**前置验证**（先做这个，零风险）：手工在 Termux 里
`adb connect 100.x.x.x:5555` 跑通脚本，确认 NAT 没挡直连
（若只能走 DERP 中继，传 APK 会很慢，方案价值下降）。

**不推荐**：cloudflared / ngrok 等公网隧道 —— ADB 无认证机制，
暴露公网 = 交出真机完全控制权。

### 8.2 `test-packer.sh` 的 flaky

`apk-protect-action/scripts/packer/tests/test-packer.sh` 里
有两处 `trap ... EXIT`（前者被后者覆盖）且各用例共用 `args.txt`，
导致 ⑫d/⑫f/⑫g 偶发失败（约 1/4 概率）。与 dpt 无关，未修。

### 8.3 已知残留的逆向面

| 项 | 为什么保留 |
|---|---|
| `JNI_OnLoad`/`JNI_OnUnload` 导出 | JNI 必需 |
| `Java_*` 业务符号导出 | dex2c 短名绑定要求，隐藏即 ULE |
| P2 只挡静态 `strings` | 动态调试试断点仍能拿到派生常量明文 |

### 8.4 用户最初设想的联动（部分已实现，未做逆向评估）

设想过："把字符串加密的类放进壳类，dex2c 把解密装抽到 so 里，
使脱壳后壳 so 仍被依赖"。

**现状**：`--dex2c-stub` 已实现大部分（桩进壳 dex + 4 方法 native 化 +
SEED 从 `JniBridge.gseed()` 取）。**但从未做过逆向对抗评估**——
脱壳者能否绕过、成本多少，没有数据。

**桩的完整链路**（要动联动必读）：
`../apk-protect-action/docs/流程文档.md` §3.7.4「两层拆分与 dex2c 联动」。
